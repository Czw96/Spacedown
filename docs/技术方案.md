# Spacedown 技术方案（性能优先）

> macOS Markdown 速览工具：Finder 空格预览（Quick Look 扩展）+ 只读多标签 App。
> **平台范围：仅 macOS。不做 iOS / iPadOS / visionOS / Mac Catalyst，不做跨平台抽象层。**
> 目标机：macOS 13+（Apple Silicon 优先）。分发：Homebrew Cask。
> 版本：v1 方案草稿 · 2026-10-07

---

## 0. 一句话结论

**性能瓶颈不在 Markdown 解析，而在 WKWebView。**

实测（50KB 文档，见 `docs/benchmarks.md`）：`stat + 读文件 + cmark 解析 + 拼 HTML` 全流程 **≈ 2.4 ms**；而 `WKWebView` 冷启动 + 载入 **≈ 40~250 ms**，占总耗时的 **90%+**。
（初稿估的是 1~3ms，实测解析一项就是 1.7ms，估乐观了约 3 倍；但结论不变，见下。）
所以整套架构的第一原则是：**把所有 CPU 工作挪到"只做一次"的缓存里，把每一次按键的开销压到只剩 `lstat()` + 一次 webview 导航，并且尽力把 webview 的开销预热/隐藏掉。**

| 路径 | 做什么 | 预期耗时 |
|---|---|---|
| 缓存命中（同一文件未修改，再按空格） | `lstat` → 命中 → `loadFileURL` | **< 50 ms（进程复用时接近瞬时）** |
| 冷启动（首次预览） | 读盘 → cmark → 拼 HTML → 写缓存 → 载入 | 60~300 ms |

### 平台范围：仅 macOS · 仅 Apple Silicon

写死这条约束，是为了避免后面反复摇摆"要不要顺手做个 iOS 版 / 要不要兼容 Intel"。它带来几个**实际的技术解锁**，不是一句口号：

| 约束 | 因此可以直接用 | 不用再为它付出代价 |
|---|---|---|
| 只做 macOS | `AppKit`（`NSWindow` / `NSTabViewController` / `NSResponder` 链） | SwiftUI 跨平台妥协、Catalyst 适配 |
| 只做 macOS | `QuickLookUI`（`QLPreviewingController` / `QLPreviewProvider`）——**iOS 上这两个类在 QuickLook 而非 QuickLookUI** | 条件编译 |
| 只做 macOS | `FSEvents`（C API，文件监听）、`NSWorkspace`、`LSSetDefaultRoleHandlerForContentType` | 跨平台 watcher 抽象 |
| 只做 macOS | `WKWebView.magnification` / `allowsMagnification`（**macOS 独有，iOS 没有**） | 自己实现捏合缩放 |
| 只做 macOS | `NSScrollView` 原生滚动、`NSEvent.addLocalMonitorForEvents` | 手势抽象层 |

**具体落地：**

- SwiftPM package 的 `platforms:` 声明 `.macOS(.v13)`（与 App target 的
  `MACOSX_DEPLOYMENT_TARGET = 13.0` 一致），不写 iOS/visionOS
- Xcode target 一律建 macOS（App / App Extension），**不建 Multiplatform**，不开 Catalyst
- 二进制 **只发 arm64，不做 universal2**：
  - 因此 C target 可以安全加 `-O3 -mcpu=apple-m1` —— 实测 **3~4% 白拿**（见 benchmarks.md）。
    ⚠️ SwiftPM 的 `cSettings` **无法按架构分支**，哪天要恢复 x86_64，这两条必须一起去掉
  - dmg 体积减半，构建时间减半
  - Homebrew Cask 加 `depends_on arch: :arm64`，Intel 机器装的时候直接给明确报错
- 沙箱 + Hardened Runtime 只对 macOS App 生效，缓存/App Group 路径一律 `~/Library/...`

**因为只做 M 系列，下面这些可以整个删掉：**

| 原方案条目 | 处置 |
|---|---|
| R4 风险「Intel 老机 WKWebView >300ms」 | **删除** —— 不存在 Intel 目标 |
| NSTextView 原生降级路径（v1 不实现） | **删除** —— 没有需要它的机器 |
| universal2 产物 | **删除** |
| 「大文件阈值待 Intel 实测再调」 | 只按 M 系列定 |

## 1. 性能目标（SLO）与度量体系

没有度量就没有性能。M1 之前先把基准套件建起来，每个里程碑卡一道性能门槛，不达标不进下一阶段。

### 1.1 指标与门槛

| # | 指标 | 目标 | 硬上限 | 测量方式 |
|---|---|---|---|---|
| P1 | QL 首帧 · 命中缓存 · ≤100KB | ≤120 ms | 200 ms | `os_signpost` + 60fps 录屏数帧 |
| P2 | QL 首帧 · 冷 · ≤100KB | ~~≤180 ms~~ **M0 实测 373ms，不达标** | 300 ms | 同上。见下方「M0 结论」 |
| P3 | QL 首帧 · 冷 · 1MB | ~~≤400 ms~~ **实测 437ms，不达标** | 700 ms | 同上 |

> **M0 实测把 P2 / P3 打穿了**（`docs/benchmarks.md` 有完整数字）：
> 冷启动 373ms 里 **300ms 是 WebContent 进程 spawn**，新建 webview 64ms，导航排版只有 10ms。
> 也就是说：**缓存省下的那 1.7ms 解析时间，相对 300ms 的进程 spawn 是零头。**
> 原方案把宝押在缓存上是押错了——真正的战场是「进程与 webview 实例的复用」。
| P4 | QL 扩展进程常驻内存 | ≤60 MB | 100 MB | `footprint` |
| P5 | 主 App 切换标签页 | ≤60 ms | 120 ms | signpost |
| P6 | 主 App 打开文件（命中缓存） | ≤150 ms | 250 ms | signpost |
| P7 | 外部修改 → 窗口内容刷新 | ≤300 ms | 500 ms | signpost（含 120ms 去抖） |
| P8 | 主 App 空转（1 标签） | ≤90 MB | 140 MB | Activity Monitor / `footprint` |
| P9 | 主 App（20 标签） | ≤250 MB | 400 MB | 同上 |
| P10 | 渲染缓存命中率（日常一周） | ≥90% | — | 埋点计数（本地，不上报） |
| P11 | 解析吞吐 | ≥28 MB/s | ≥25 MB/s | Bench CLI（**实测 25~29 MB/s**，初稿估 60 是错的） |

> P1 的"首帧"定义：**从 `beginRequest(with:)` / `preparePreviewOfFile` 被调用 → WKWebView 首次 `didFinish` 导航**。
> 用户感知口径另用 60fps 录屏数帧核对（signpost 看不到 QL 面板动画掩盖掉的时间）。

### 1.2 基准套件（M1 交付，先于 UI）

- `Sources/Bench`：独立可执行 target，`spacedown-bench <corpus-dir> --iter 200`
- 语料：1KB / 10KB / 50KB / 500KB / 5MB 五档 × 三类（纯文本 / 重表格+代码块 / 病态输入：深层嵌套引用、万级列表项）
- 分阶段打点：`stat` / `read` / `parse` / `assemble` / `cacheWrite` / `webviewLoad` / `total`
- 输出 p50 / p95 / p99 + RSS 峰值，结果写进 `docs/benchmarks.md`，每次里程碑更新
- 主 App 内隐藏 Debug 面板（⌘⌥B）显示实时耗时，便于真机排查

## 2. 总体架构

```
┌─────────────────────────┐        ┌──────────────────────────┐
│  Spacedown.app          │        │  QuickLookExtension.appex │
│  (AppKit 只读查看器)      │        │  (com.apple.quicklook… ) │
│  ─ WKWebView (LRU 池)    │        │  ─ 1 个预热 WKWebView     │
│  ─ 多标签 / 文件监听      │        │  ─ QLPreviewingController │
└───────────┬─────────────┘        └────────────┬─────────────┘
            │                                    │
            └──────────► MarkdownKit ◄───────────┘
                    (cmark-gfm C + Swift 封装)
                              │
                              ▼
                        RenderCache（磁盘）
              ~/Library/Group Containers/cn.29dev.spacedown.shared/
                        或 ~/Library/Caches/cn.29dev.Spacedown/
```

三个可复用模块，主 App 与扩展**共用同一份缓存**，这是命中率的关键：
在 App 里打开过的文档，回到 Finder 按空格直接命中，反之亦然。

| 模块 | 职责 | 必须可独立测试 |
|---|---|---|
| `MarkdownKit` | cmark-gfm 封装、HTML 拼装、缩放/滚动注入 | ✅（Bench CLI 直接跑） |
| `RenderCache` | stat 校验、读写、LRU 淘汰、App Group 路径 | ✅ |
| `SharedTheme` | CSS 模板（明暗自适应） | ✅ |

工程形态：**Xcode project + 本地 SwiftPM package**（`.appex` 的 Info.plist / 签名 / 嵌套 bundle 用 SwiftPM 纯命令行太痛苦）。
`MarkdownKit` / `RenderCache` 作为 local package，Bench CLI 作为其中 executable target。

## 3. 渲染管线（冷路径，逐步预算）

| 步 | 操作 | 预算（50KB） | 关键实现要点 |
|---|---|---|---|
| 1 | `lstat(path)` | ~0.02 ms | 取 dev / inode / size / mtime(nsec) 四元组 |
| 2 | 缓存校验 | ~0.05 ms | 读 `.meta` 比对四元组 + `renderVersion` |
| 3 | 读文件 | ~0.3 ms | `Data(contentsOf:options:.mappedIfSafe)` → mmap，**零拷贝** |
| 4 | UTF-8 → cmark | 0 ms | **不建 Swift String**：`withUnsafeBytes` 把裸指针直接喂给 `cmark_gfm_markdown_to_html` |
| 5 | cmark-gfm 解析 | **1.7 ms**（实测） | 静态链接 + release `-O`；吞吐实测 28.5 MB/s |
| 6 | 拼 HTML | ~0.3 ms | **用 `Data` 追加，不做 Swift 字符串拼接**：`head+CSS` 前缀 + body + 后缀 |
| 7 | 落缓存 | ~0.5 ms | **后台队列 + tmp→rename 原子替换**，不在关键路径 |
| 8 | WKWebView 载入 | **40~250 ms** | `loadFileURL(_:allowingReadAccessTo:)` |

**关键取舍 3 条：**

1. **第 4 步不建 String。** `String(decoding:as:)` 会做 UTF-8 校验 + 一次全量拷贝（5MB 文件 ≈ 5~10 ms + 5MB 内存峰值）。cmark 本来就要 C 字符串，直接给指针。
2. **第 6 步用 Data 不用字符串插值。** 每次预览都要内联一份 ~6KB CSS；把它在进程启动时预加载成 `Data` 常量，拼装时纯 memcpy。
3. **第 7 步异步。** 缓存写入失败只影响下次命中，不影响本次显示；缓存损坏时回退到重新渲染。
4. **别在解析上过度优化。** 实测固定开销约 0.04ms（`cmark_parser_new` 的 arena 分配），
   把扩展指针缓存成 static 的收益是 **0**（噪声内）。解析侧已经够快，优化预算应该全部投给 webview。

### 3.1 大文件兜底

**M0 实测后，大文件的账要重算。** 解析是线性且便宜的（1MB ≈ 40ms、5MB ≈ 200ms，且能被缓存归零），
但**排版才是真正的天花板**：实测 ≈ **236 ms / MB(HTML)**，而 HTML 约为 Markdown 的 1.85 倍 →

| Markdown | 解析 | **排版（webview）** | 合计 | 策略 |
|---|---:|---:|---:|---|
| 100KB | 4 ms | 44 ms | 48 ms | 正常 |
| 500KB | 20 ms | 218 ms | 238 ms | 正常（上限） |
| 1MB | 40 ms | **437 ms** | 477 ms | ❌ 超 P3 |
| 2MB | 80 ms | 874 ms | 954 ms | ❌ |

> ⚠️ **原方案的「1~4MB 跳过图片内联与语法高亮」是无效缓解** —— 成本是整篇 HTML 的排版，
> 省这些不解决。**唯一有效的手段是截断文档。**

| 大小 | 策略 |
|---|---|
| ≤ 500 KB | 正常全量渲染 |
| > 500 KB | 截断到前 500KB 预览 + 顶部提示条，用户可点「仍要渲染全文」 |

> 后续若发现排版能靠 `content-visibility: auto` 之类的 CSS 做虚拟渲染优化，阈值可以再放宽——
> 这是 M5 值得试的一项。
>
> 病态输入防护：实测 335KB 病态输入 28.9 ms（11.3 MB/s），是**线性劣化不是指数爆炸**——cmark 的 AFL 结论成立，不需要自己做递归深度限制。另外给 webview 载入加 5s 超时，超时降级为纯文本预览。

## 4. 缓存设计（本方案的性能核心）

### 4.1 键与校验

```
cacheDir/<sha1(path)[0:2]>/<sha1(path)>.html
cacheDir/<sha1(path)[0:2]>/<sha1(path)>.meta   // JSON: dev, inode, size, mtimeNsec, renderVersion
```

- **Key**：路径的 SHA-1（不用 inode，路径稳定且可读）。目录按前 2 位分片，避免单目录万级文件。
- **校验**：`lstat()` 一次，比对 `dev + inode + size + mtimeNsec` 四项。**不读文件内容、不算内容哈希** —— 这是"瞬时"的前提。
  - 为什么要 inode：vim / VS Code 等原子保存是 `写临时文件 → rename`，路径不变但 inode 变；只比 mtime 在某些文件系统（HFS+ 秒级精度、网络盘）会漏。
- **renderVersion**：CSS 模板 / 解析器版本变了，只改一个整数就全量失效，不需要清目录。
- **命中路径**：`lstat` → 读 `.meta`（~100B）→ `loadFileURL`。**完全没有文件读取与解析。**

### 4.2 淘汰

- 容量上限：**2000 条 或 256 MB**（先到先算）
- 淘汰依据：缓存文件的 `contentModificationDate`（**不更新 atime**，省一次 write 系统调用；命中率损失可接受，因为真正热的文档会在 LRU 池里）
- 触发时机：写入后异步检查，**最多每 60s 执行一次**，且只在超限时列目录

### 4.3 单文件自包含

缓存的 HTML **必须零外部依赖**：CSS 内联、图片 base64 内联、无 JS（基线）、无网络请求。
好处：一次导航 = 一个资源，无子资源瀑布；跨进程（App ↔ 扩展）搬运不需要附带目录；沙箱下不需要额外文件访问权限。

- 图片内联上限：单张 ≤ 2 MB，总计 ≤ 20 MB；超限降级为占位符
- 安全：**四层，缺一不可**（初稿只写了 CSP 一层，实测证明不够，见下）

### 4.4 裸 HTML：必须开 `CMARK_OPT_UNSAFE`，但要配四层防护

这是本方案里**唯一一处被实测推翻过两次**的地方，写细一点。

**为什么必须开。** cmark 默认（`CMARK_OPT_DEFAULT`）会把文档里**所有**裸 HTML 替换成
`<!-- raw HTML omitted -->`。后果：真实 README 顶部的徽章行（`<p align="center">` + `<img>`）、
`<details>`、`<kbd>`、`<br>` 整片消失，预览看起来像坏了——与"渲染要好看"直接冲突。

**开之后的四层防护：**

| # | 层 | 拦什么 | 位置 |
|---|---|---|---|
| 1 | `tagfilter` 扩展 | `<script>` `<style>` `<iframe>` `<title>` `<textarea>` `<xmp>` `<noembed>` `<noframes>` `<plaintext>` | **必须传给 `cmark_render_html()` 的第三个参数**，挂 parser 上不生效 |
| 2 | 危险 scheme 过滤 | `javascript:` `vbscript:` `data:text/html` → 换成 `#blocked-` | `MarkdownRenderer.neutralizingDangerousURLs`，**字节级扫描** |
| 3 | CSP `default-src 'none'` | 脚本执行、一切远程加载；WebKit 下挡 `javascript:` 导航 | `SharedTheme.htmlPrefix` |
| 4 | 沙箱 | 文件系统访问 | App / 扩展 entitlements |

**两个必须避开的坑（都实测踩过）：**

- `String.range(of:options:.caseInsensitive)` 扫大字符串只有约 **4.5 MB/s**，
  用它做第 2 层会把 50KB 渲染从 1.65ms 打到 **33ms（20 倍回归）**。必须手写字节扫描。
- `cmark_node_get_url()` 返回 arena 分配的串，**手动 `free()` 会 double free**。

## 5. 视觉设计

### 5.1 明暗主题：一次渲染，两套配色

**绝不为主题切换重新渲染，也绝不在 webview 里跑 JS 换肤。**

```css
:root { color-scheme: light dark; --text:#1b1b1f; --bg:#ffffff; ... }
@media (prefers-color-scheme: dark) {
  :root { --text:#e9e9ec; --bg:#1b1b1d; ... }
}
```

- WKWebView 自动响应系统 `prefers-color-scheme` 变化，**切换瞬间生效、零成本、无闪烁**
- 缓存只存一份 HTML，主题切换不影响命中率
- 反过来：如果做成"渲染时决定配色"，系统一换主题，全库缓存集体失效 —— 这是必须避开的坑

### 5.2 内容排版

落地在 `Packages/Core/Sources/SharedTheme/theme.css`（唯一来源，改样式只改这一个文件）。
取向是**克制**：中性色阶打底，全篇只有一个强调色，层级靠字号 + 字重 + 留白表达，**不靠边框和色块**。

| 项 | 取值 | 为什么 |
|---|---|---|
| 行宽 | `max-width: var(--measure)`，默认 `100%` = **铺满可用宽度**；可在「显示 → 版心宽度」调到 40~100%（步进 10%，⌥⌘= / ⌥⌘− / ⌥⌘0） | 曾写死 `44rem`：在 960pt 窗口里两侧各空 122pt，整块内容挤成中间一条（2026-10-10 反馈）。**不再写死具体宽度** —— "完全自适应"与"一行太长"是同一个旋钮的两端，该由用户定，代码里只留一个比例 |
| 正文 | 16px / 1.72 | 中英混排的行高要留足 |
| 字体栈 | `-apple-system, "SF Pro Text", …, "PingFang SC", …` | **PingFang SC 必须在 fallback 之前**，否则中文回退到别的字体 |
| 标题字距 | h1 `-0.024em` → h6 `0.02em` | 大字号收字距、小字号放字距，这是"精致感"的来源 |
| 强调色 | 浅 `#4f46c9` / 深 `#9b93f2` | 只出现在链接、选中、任务勾选上 |
| 深色底 | `#1b1b1d`（不是纯黑） | 纯黑在 OLED 上会有光晕感；正文也不用纯白 |

几个容易被忽略、但直接影响观感的细节：

- **行内代码**：轻底色 + 4px 圆角，**不加边框**
- **代码块**：`--surface` 底色 + 1px hairline + 10px 圆角，字号 0.855rem
- **表格**：只有横向 hairline，没有竖线、没有斑马纹；`font-variant-numeric: tabular-nums` 让数字列对齐
- **引用**：左侧 3px 竖线 + 次要文字色，**不做成一个灰色块**
- **任务列表**：原生 checkbox 在深色模式下很难看 → `appearance: none` 后用 CSS 重画（含勾选对勾）
- **链接**：下划线用 `text-underline-offset: 0.18em` + 1px 细线，默认下划线颜色是强调色的 10% 透明，hover 才变实
- **下划线偏移**：没有它，中文链接的下划线会和字粘连

### 5.3 窗口与标签栏（AppKit）

| 部件 | 方案 |
|---|---|
| 窗口 | `NSWindowStyleMask.fullSizeContentView` + 标题栏隐藏，交通灯与自绘标签栏同一行 |
| 标签栏材质 | `NSVisualEffectView`（`.windowBackground`）—— 原生毛玻璃，不要自己画 |
| 标签栏高度 | 38px；标签最大宽 180px，过长中间截断；关闭按钮 hover 才出现 |
| 当前标签 | 底色微抬 + 顶部 2px 强调色条（**不要用边框把标签框起来**） |
| 工具栏 | **只有缩放** `−` / 百分比 / `+`，贴右缘，与标签区之间一条 1pt 分隔线。**版心宽度不放这里**（2026-10-11 试过并排两组 `− x +`，噪声大于收益，已撤），它只在「显示 → 版心宽度」里。~~「在 Finder 中显示」「用默认编辑器打开」~~ 已从工具栏移除（2026-10-10），只在「文件」菜单里（<kbd>⌘</kbd><kbd>⇧</kbd><kbd>R</kbd> / <kbd>⌥</kbd><kbd>⌘</kbd><kbd>E</kbd>） |
| 动效 | 标签切换 120ms 交叉淡入；hover 100ms；**不用弹性动画** |
| 滚动条 | WebKit 私有样式，11px，滑块带 3px 背景色描边 |

> 反例约束：不加渐变、不加卡片阴影堆叠、不用 emoji 当图标、不用全宽分隔线切分区块。

> ⚠️ 缩放三件套（`−` / 百分比 / `+`）必须落在**同一条中线上**。
> **中间那格不能照抄按钮的框位置** —— `NSTextField` 的文字是贴着框顶排的，而按钮里的
> SF Symbol 是在方框里居中的；两者框一对齐，数字反而会比 `−`/`+` **高约 4pt**
> （错得比"凭感觉写死一个 y"还多）。正解是按字体度量反推：让**数字的 cap 高中线**
> 落在按钮方框的中线上 —— 见 `TabBarView.zoomLabelFrame`。
> 验收：`DebugLayout` 日志里三条 `centerFromTop` 应当相等（实测均为 19.0）。

## 6. Quick Look 扩展

### 6.1 形态选择

**macOS 15 Sequoia 起，第三方 `.qlgenerator` 已不再被支持**，只能走 App Extension（`.appex`）。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A · 数据型 `QLPreviewProvider` | 返回 `QLPreviewReply`，把 HTML 交给 QL 自己渲染 | **扩展进程完全不建 webview**，省掉实测 300ms 的进程 spawn + 64ms 的实例创建 | 对缩放快捷键/主题无控制权；图片等子资源权限难处理；QL 内建 HTML 渲染行为各版本不一致 | **M2 先做它的 spike** |
| B · 视图型 `QLPreviewingController` | 自建 `NSViewController` + `WKWebView` | 完全掌控：滚动、⌘±缩放、主题、图片、空状态 | 冷启实测 **373ms**，已超 P2 上限 | 保真度不足时的回退 |

⚠️ **M0 实测后改了主意：先做 A，不是 B。**

理由是本项目的第一原则是性能，而 373ms 里 300ms 是 WebContent 进程 spawn ——
数据型方案根本不建 webview，这笔钱全省。QL 自己的渲染服务是常驻的，很可能直接给出几十毫秒的首帧。

决策链：**M2 先用 A 做一个能跑的 spike，实测首帧；只有当你对 QL 渲染出的观感/交互不满意时，才回退到 B。**
（对照：`/Applications/showmd.app` 这个已上架的同类产品用的是 B —— 但它的第一原则未必是性能。）

⚠️ **2026-10-08 决策反转：A 已落地过、被实测推翻，现在是 B。**

用户反馈「预览太慢、向下滚动画面太卡」。归因（工具 `Packages/Core/Sources/ScrollBench/`，
数据与推理见 `docs/性能分析.md §6`）指向一个 A 方案无法解决的环节：

- **A 的代价被低估了。** 它省掉的是 webview 创建，但**失去了对 web view 尺寸与滚动的全部控制** ——
  而实测证明「滚动卡」正是从那里来的：同一份 HTML 在 **viewport 尺寸**的 `WKWebView` 里，
  连 47 万 px 高、2.8 万节点的文档、以 9000 px/s 猛甩也是 **60.0 fps / 0 漏帧**。
  也就是说 WebKit 画得动，问题只在「谁在承载、按多大尺寸承载」。
- **A 还让这个项目对 QL 变成零可见度**：Quick Look 主进程会沙箱化扩展进程，
  `try?` 往 `~/Library/Logs` 与 `/tmp` 写日志**全部静默失败**（那个 `timing.log` 从未出现过），
  于是连「慢是多少 ms」都拿不到。B 之后改用 `os_log`，才能埋点。

所以：**形态为 B（视图型）**。下面那三招照旧适用，其中第 2 招已实现为
`PreviewWebViewPool`（容量 1，退场后延迟 0.5s 回收；只有确认过回收可达才预热下一份，
避免白建实例）。第 1 招（`beginRequest` 即预热）没做 —— 视图型扩展的入口是
`preparePreviewOfFile`，在它之前没有我们能跑的代码。

若最终走 B，用下面三招把 webview 成本压掉：

1. **进程启动即预热**：在 `beginRequest(with:)`（`NSExtensionRequestHandling`）里就创建 `WKWebView` 并载入一个 `about:blank`（或最小骨架 HTML），让 WebContent 进程先起来。这一段时间与 QL 面板动画重叠，等于白赚。
2. **进程内复用**：QL 对连续预览会复用同一个扩展进程 → 用一个 module 级单例持有 webview，第二次起就是"已热"状态。
3. **命中缓存走 `loadFileURL`**：不用 `loadHTMLString`（大字符串要额外编码 + IPC 传输）。

### 6.2 注册与 UTI

`Info.plist`：

```xml
NSExtensionPointIdentifier = com.apple.quicklook.preview
NSExtensionPrincipalClass  = $(PRODUCT_MODULE_NAME).PreviewViewController
QLIsDataBasedPreview       = false
QLSupportedContentTypes    = [ cn.29dev.spacedown.markdown,
                               net.daringfireball.markdown ]
```

✅ **M0 已实测清楚，不再是不确定项。**

本机逐个扩展名探测（`mdls -name kMDItemContentType`）：

| 扩展名 | 实际 UTI | 被谁占了 |
|---|---|---|
| `.md` | `net.daringfireball.markdown` | 系统/通用，放心用 |
| `.markdown` | `net.daringfireball.markdown` | 同上 |
| `.mdown` `.mkd` | `com.kingsoft.wpsoffice.markdown` | **WPS** |
| `.mkdn` `.mdtxt` | `one.yetanother.showmd.mdown` | **showmd** |
| `.mdwn` | `dyn.ah62d4rv4ge8043d1r2` | 动态 UTI，无人认领 |
| `.rmd` `.qmd` `.mdx` | `one.yetanother.showmd.*` | **showmd** |

**结论（照抄已上架的 `/Applications/showmd.app` 的做法，它是验证过的）：**

1. `QLSupportedContentTypes` = `["net.daringfireball.markdown", "public.markdown"]` ——
   我们已经只需要 `.md`/`.markdown`，这两个 UTI 就够了
2. **不要导出自己的 `md` UTI。** 我原方案里"自导出 `cn.29dev.spacedown.markdown` 认领 md"是错的——
   每个扩展名都已被先装的 App 抢走，我们也去认领就是**抢别人的类型**，会破坏其它 App。
   showmd 的实证做法正是：只认 `net.daringfireball.markdown`，且只导出**无人认领**的扩展名
3. **绝不列 `public.plain-text`** —— 实测 `.md` 的 conform 链里就有它（`public.item → public.text →
   public.plain-text → net.daringfireball.markdown`），列了会劫持所有 `.txt` 预览
4. 扩展入口**再做一次路径后缀兜底判断**（白名单内才渲染，其余立刻 `completionHandler(nil)`）

排查命令：`mdls -name kMDItemContentType foo.md`
（⚠️ `pluginkit -m` 在受限环境会报 `unauthorized discovery flag`，`qlmanage -p` 会报
`sandbox initialization failed`，别误判成 QL 坏了。）

### 6.3 滚动与缩放

| 能力 | 实现 |
|---|---|
| 滚动 | WKWebView 原生响应滚轮/触控板，无需额外代码 |
| ⌘+ / ⌘- / ⌘0 | 改 `webView.pageZoom` —— **会重排**（视口跟着变窄、内容折行），所以放大后**不会压出横向滚动条** |
| ~~捏合缩放~~ | **已关**（不再开 `allowsMagnification`）。它属于"视觉缩放、不重排"，一放大必然压出横向滚动条 —— 与"放大不要横向滚动条"直接冲突，而且两套缩放叠加会互相干扰。缩放只保留 `pageZoom` 一条路 |

⚠️ **滚动这条的唯一踩坑点：web view 的尺寸。**
`loadView()` 里把 `WKWebView` 的 frame 设成**容器 bounds 并跟着自适应**
（`autoresizingMask = [.width, .height]`），**绝不能按整篇文档高度撑开** ——
撑开之后每一帧都要主线程同步重绘整屏，就是用户抱怨的那个「滚动卡」。
2026-10-08 实测：viewport 尺寸下 47 万 px 的文档也是 60.0 fps / 0 漏帧（`docs/性能分析.md §6`）。

⚠️ 风险：QL 面板可能吞掉键盘事件。M0 必须验证；若被吞，降级为「捏合缩放 + 预览内嵌缩放按钮」。

## 7. 主 App（只读查看器）

### 7.1 技术选型：AppKit，不用 SwiftUI

- 多标签、窗口操作、⌘W/⌘M、自定义标签条 → AppKit 控制力更强
- 启动开销更小、行为更可预测（性能优先）
- SwiftUI 只在「设置 / 关于」这类静态页用

### 7.2 多标签：LRU webview 池

| 方案 | 切换成本 | 内存 | 结论 |
|---|---|---|---|
| 每标签一个 WKWebView | ~0 ms | 20 标签 ≈ 400~800 MB | ✗ |
| 单 webview + 换文档 | 30~80 ms | 恒定 | △ |
| **LRU 池（默认 5，且淘汰不销毁实例）** | 命中池内 ≈ 0 ms，池外 ≈ 74 ms | 恒定上界 | **✓** |

- **M0 实测修正**：新建 webview 74ms、二次导航只要 10ms，差 7 倍。
  所以池子从"默认 3"上调到 **5**，并且**淘汰时只把实例摘下来放进备用区，不销毁**
  —— 销毁后要用就得付 74ms 重建费，而一个空 webview 常驻的成本远低于此。
- 被淘汰的标签序列化 `scrollY` 到模型，回来时 JS 恢复滚动位置
- **预测性预载**：⌘⇧[ / ⌘⇧] 按下前，把"相邻标签"在后台 webview 预渲染（二期）
- 快捷键：`⌘⇧[` / `⌘⇧]` / `⌃Tab` / `⌘1~9` / `⌘W`

### 7.3 文件监听（外部修改自动刷新）

| 方案 | 适用 | 结论 |
|---|---|---|
| 每文件一个 `DispatchSource` | ≤ 20 个文件 | 简单，够用 |
| **单条 FSEvents 流 + `kFSEventStreamCreateFlagFileEvents`** | 任意规模 | **✓ 推荐**，一条流管所有父目录，系统级合批 |

- 去抖 **120 ms**（编辑器保存常触发多次 write）
- 去抖后 `lstat` 比对四元组，**没变就不重渲染**（这是省 CPU 的大头：一次保存可能触发 5~10 个事件）
- 重渲染走后台队列，完成后切回主线程替换；**保持滚动位置**
- 渲染请求带 `generation` 序号，过期的直接丢弃（协同式取消）

### 7.4 窗口与只读

- 关闭 / 最小化 / 全屏：AppKit 标准行为
- 只读：HTML 天然不可编辑；允许选中复制（有价值），禁用一切输入交互
- `LSHandlerRank = Alternate`：默认**不抢**用户的编辑器成为默认打开方式；首次启动提供「设为默认打开方式」按钮（`LSSetDefaultRoleHandlerForContentType`）

## 8. 关键选型对比

### 8.1 Markdown 解析器

| 候选 | 实现 | 相对速度 | GFM（表格/任务列表） | 结论 |
|---|---|---|---|---|
| **cmark-gfm（vendored C）** | C | **1×（基准）** | ✅ | **✓ 推荐** |
| Down / Down-gfm | Swift 包 cmark | ~1.2×（多一层 AST→HTML） | ✅ | 备选，省事 |
| Ink | 纯 Swift | ~5~10× | ❌ | ✗ |
| apple/swift-markdown | 纯 Swift | ~10~20× | ❌ | ✗ |
| JS（markdown-it in JSC） | JS | ~50×（含 JIT 预热） | ✅ | ✗ 绝对不碰 |

**推荐做法**：把 `cmark-gfm` 的 C 源码 **vendor 进仓库作为 SwiftPM 的 C target**（约 30 个 `.c`），`-O3` 编译。
理由：无网络依赖、构建可复现、可裁剪掉不需要的扩展、可精确控制编译选项 —— 对一个"性能最重要"的小工具，这比拉一个三方包更可控。
Swift 侧封装只有 ~40 行：`parse(bytes:) -> Data`。

### 8.2 渲染载体

| 候选 | 冷启 | 内存 | 表格/代码/图片保真 | 结论 |
|---|---|---|---|---|
| **WKWebView** | 40~250 ms | 50~100 MB | **高**（表格 / 代码块 / 图片 / `<details>` 全都能正常渲染） | **✓ 唯一路径** |
| NSTextView + NSAttributedString | 20~40 ms | ~10 MB | 中（`NSTextTable` 做表格吃力，裸 HTML 无从下手） | ✗ 已排除 |

> 只做 M 系列之后，NSTextView 降级路径**整个删掉** —— 它当初存在的唯一理由是"Intel 老机可能不达标"，
> 而这个目标机不存在了。少一条渲染路径 = 少一份要维护的样式分叉。

## 9. 分发与卸载

### 9.1 签名

- Developer ID Application + **Hardened Runtime** + timestamp

### 9.2 Homebrew Cask

自建 tap `29dev/homebrew-tap`：

```ruby
cask "spacedown" do
  version "1.0.0"
  sha256 "<dmg sha256>"
  url "https://github.com/29dev/spacedown/releases/download/v#{version}/Spacedown-#{version}.dmg"
  name "Spacedown"
  desc "Finder 空格键速览 Markdown"
  homepage "https://29dev.cn/spacedown"
  depends_on macos: ">= :ventura"     # QLPreviewingController 视图型方案，部署目标 13.0

  app "Spacedown.app"

  postflight do
    system_command "/usr/bin/qlmanage", args: ["-r"]
  end

  zap trash: [
    "/Applications/Spacedown.app",
    "~/Library/Caches/cn.29dev.Spacedown",
    "~/Library/Application Support/Spacedown",
    "~/Library/Preferences/cn.29dev.Spacedown.plist",
    "~/Library/HTTPStorages/cn.29dev.Spacedown",
    "~/Library/Saved Application State/cn.29dev.Spacedown.savedState",
    "~/Library/WebKit/cn.29dev.Spacedown",
    "~/Library/Group Containers/cn.29dev.spacedown.shared",
  ]
end
```

- 安装：`brew install --cask 29dev/tap/spacedown`（tap 可设默认，最终做到 `brew install --cask spacedown` 取决于是否进 homebrew/cask 主仓）
- **卸载无残留**：`zap` 覆盖上述全部路径；`brew uninstall --zap` 执行。App 不往 `/Library` 写任何东西（不装 `.qlgenerator`、不装 LaunchAgent）

### 9.3 缓存放在哪：App Group vs 各自容器

| 方案 | 命中率 | 残留 |
|---|---|---|
| **App Group `cn.29dev.spacedown.shared`** | **高**：App 打开过的文档，Finder 按空格直接命中 | `~/Library/Group Containers/...`（zap 已覆盖） |
| 各自容器 | 减半 | 少一条路径 |

**推荐 App Group** —— 命中率是本产品的核心体验指标，多一条 zap 路径的代价可以接受。

## 14. 工程结构与构建（Xcode / SwiftPM 双链路）

### 13.1 为什么 Xcode 工程里**不引用** SwiftPM 包

原本的设计是 `Spacedown.xcodeproj` 里加一条 `XCLocalSwiftPackageReference` 指向 `Packages/Core`，
让 `MarkdownKit` / `SharedTheme` 以 SwiftPM 产品形式被引用。2026-10-08 实测**走不通**：

```
Resolve Package Graph
xcodebuild: error: Could not resolve package dependencies:
  sandbox-exec: sandbox_apply: Operation not permitted
```

根因：Xcode 接 SwiftPM 包时先编译 `Package.swift` manifest，而 SwiftPM 会把 manifest 编译
塞进 `sandbox-exec`。本机（以及任何带沙箱的 shell / CI）里，**带 `deny` 规则的 profile 一律
过不去** —— 连 `(version 1)(deny default)` 都返回 `Operation not permitted`（实测：

```
sandbox-exec -p '(version 1)(allow default)' /bin/echo     → ok
sandbox-exec -p '(version 1)(deny default)'  /bin/echo     → sandbox_apply: Operation not permitted
```

）。试过并排除的路：`--disable-sandbox` 没有 xcodebuild 对应开关；
`SWIFTPM_DISABLE_SANDBOX` / `SWIFTC_DISABLE_SANDBOX` 等环境变量均无效（二进制里只有
`-disable-sandbox` 一个命令行 flag）；`xcodebuild -disableAutomaticPackageResolution` 仍要
加载 manifest，一样挂。

**结论：改成原生 target。** Xcode 工程直接编译 `Packages/Core` 下的源码，`swift build`
照旧走 SwiftPM，两条链路互不依赖。代价是新增 3 个 target，收益是构建不再依赖 sandbox。

### 13.2 target 划分

| Target | 类型 | 内容 | 说明 |
|---|---|---|---|
| `CcmarkGfm` | static library (C) | 34 个 `.c` | `MODULEMAP_FILE` 指向 `Packages/Core/XcodeSupport/CcmarkGfm/module.modulemap` |
| `MarkdownKit` | framework | `MarkdownRenderer.swift` | 内部静态链 `libCcmarkGfm.a`，宿主不需要 embed 它 |
| `SharedTheme` | framework | `Theme.swift` + `theme.css` | CSS 走 framework 自己的 Resources |
| `Spacedown` | App | SwiftUI 占位窗口 | 目前唯一职责是**承载 `.appex`** |
| `QuickLookPreview` | app-extension | `PreviewProvider.swift` | 数据型 QL 扩展 |

为什么 `MarkdownKit` / `SharedTheme` 用 framework 而不是 static library：framework 靠 `-F`
自动发现，`import` 一定成立；static library 要额外配 swiftmodule 搜索路径，多一处易碎点。

### 13.3 `SharedTheme` 的两套 bundle 定位

```swift
private static var cssBundle: Bundle {
#if SPACEDOWN_SPM_BUILD
    Bundle.module            // SwiftPM：resource bundle
#else
    Bundle(for: ThemeToken.self)   // Xcode：framework 自己的 bundle
#endif
}
```

`SPACEDOWN_SPM_BUILD` 由 `Package.swift` 用 `swiftSettings: [.define(...)]` 注入。
注意 Xcode 侧**不能**用 `Bundle.main` —— 那时它是宿主 App / appex，里面没有 `theme.css`。

### 13.4 工程文件是脚本生成的

`project.pbxproj` 由 `scripts/gen_project.py` 生成，加源码文件 / 加 target 后重跑一次即可。
手写 pbxproj 漏一个 UUID 引用只会得到 `object not found`，排查成本很高。

### 13.5 本次踩的坑（都实际报错过）

| 现象 | 原因 | 解法 |
|---|---|---|
| `Unable to read project` / `not a valid property list` | `DYLIB_INSTALL_NAME_BASE = @rpath;` —— 旧式 plist 不允许裸 `@` | 加引号 `"@rpath"` |
| `The file "theme.css" couldn't be opened` | `PBXGroup` 嵌套时，子组的 `path` 不与父组拼接（父组同时有 `name` + `path` 时尤其明显） | 组全部扁平挂在 `mainGroup` 下，路径从仓库根写全 |
| `Unable to resolve module dependency: 'CcmarkGfm'` | `MarkdownKit` 的 swiftmodule 带着对 `CcmarkGfm` 的依赖，凡 `import MarkdownKit` 的 target 都得能找到它的 modulemap | `SWIFT_INCLUDE_PATHS` 提到**工程级** |
| `Cannot code sign ... does not have an Info.plist` | framework target 也要 Info.plist | `GENERATE_INFOPLIST_FILE = YES` |
| `contextual closure type '(QLPreviewReply) throws -> Data' expects 1 argument` | ObjC 的 `NSError**` 参数被 Swift 吞掉，变成 `throws` | 失败要 `throw`，不是给 errorPointer 赋值 |

### 13.6 签名

本机 `security find-identity -v -p codesigning` 返回 **0 个身份**，只能 ad-hoc
（`CODE_SIGN_IDENTITY = "-"`, `ENABLE_HARDENED_RUNTIME = NO`）。M6 公证分发时必须换成
Developer ID 并打开 Hardened Runtime。

## 15. 运行时踩的坑（都是"进程在跑、但什么都没发生"这一类）

这三个都是实测才发现、而且**不崩溃、不报错、不写系统日志**的问题，靠打点日志才定位到。
记录在这里是因为它们都会以"看起来在工作"的形态骗过验证。

### 15.1 `@main` 标在 `AppDelegate` 上 → delegate 从来没被实例化

AppKit 为 `NSApplicationDelegate` 提供的默认 `main()` 只有一行：

```swift
extension NSApplicationDelegate {
    public static func main() {
        exit(NSApplicationMain(CommandLine.argc, CommandLine.unsafeArgv))
    }
}
```

而 `NSApplicationMain` 是靠 **nib**（`NSMainNibFile`）来创建 delegate 并连线的。
本工程是纯代码启动、没有 nib → **`AppDelegate` 永远不实例化** →
`applicationWillFinishLaunching` / `application(_:open:)` 一个都不触发 → 不出现任何窗口。

表象极具误导性：**进程正常起来并常驻、不崩溃、没有崩溃报告**。
之前"主 App 实测可打开（进程在跑、无崩溃）"就是这么误判的。

**解法**：自己写入口（`SpacedownMain.swift`），手工 `app.delegate = ...` 后再 `run()`。
⚠️ 注意 `NSApplication.delegate` 是 **weak** 的，必须自己强引用住 delegate。

### 15.2 给 `load()` 传文件目录作 `baseURL` → WebKit 死锁

`load(_:mimeType:characterEncodingName:baseURL:)` 传文件所在目录，WebKit 会走
`WebProcessProxy::assumeReadAccessToBaseURL` → `SandboxExtension::createHandle`
→ `_sandbox_extension_issue` 去申请"读该目录"的沙箱扩展。实测死锁：

```
主线程   : loadData → assumeReadAccessToBaseURL → _sandbox_extension_issue → __mac_syscall   [阻塞]
后台线程 : SQLiteDatabase::open → initializeSQLiteIfNecessary
           → callOnMainThreadAndWait → __psynch_cvwait                                     [等主线程]
```

表象：**主线程永久卡死，进程还在、不崩溃、日志停在半句**。用 `sample <pid>` 抓栈才看清。

**解法**：换一个**非 file** 的 baseURL（我们用 `about:blank`）。WebKit 源码里那个函数
第一句就是 `if (!url.isLocalFile()) { done(); return; }`，整段绕开。
反正 HTML 是单文件自包含的（CSP `default-src 'none'`），baseURL 只影响相对 URL 解析。

### 15.3 每个 `WKWebView` 独占一个 WebContent 进程 —— 池容量 = 进程数上界

一度以为"每个 webview 一套进程"是因为各自造了 `WKWebViewConfiguration`（进程池不共享），
于是改成共用一份 configuration —— **实测进程数一个没少**（3 个标签仍是 3 个进程）。

`WKProcessPool.h` 给了权威答案：

> *Each web view is given its own web content process until an implementation-defined
> process limit is reached; after that, web views with the same process pool end up
> sharing web content processes.*

而且 `WKProcessPool` 自 **macOS 12 起已弃用**（"Creating and using multiple instances of
WKProcessPool no longer has any effect"）。**共用 configuration 换不来进程复用**，改动已撤回。

**这条结论真正的意义在于**：`WebViewPool` 的容量**同时就是活着的渲染进程数上界**
（5 + 备用 2 = 最多 7 个）。§1.1 里 P9（20 标签 ≤ 250MB）能成立，全靠这个上限；
改成"每标签一个 webview"就是 20 个进程、600MB 起。

**另一个实测数字**（预热之后，本机）：

| 场景 | 首帧 |
|---|---:|
| 第一个文件（预热过的 webview） | **98.0 ms** |
| 第二个文件（新 webview、新进程） | **99.0 ms** |
| 三个文件并发 | 152 ~ 185 ms |

也就是说：进程启动费**只有第一个特别贵**（M0 实测 373.6ms），第二个进程只要 ~99ms ——
系统层面 dyld 缓存与 XPCServices 已经热了。所以预热的收益集中在"第一次打开"，
后续标签按 ~100ms 计。这和 M0 的 73.8ms 是同一量级，模型没变。

### 15.4 交通灯位置：要"量按钮、移按钮、并且自愈"

标签栏 38pt，交通灯默认按标题栏（约 32pt）居中 → 两者差 3pt，要往下挪。

踩了三层：

1. 一开始平移的是按钮的**父视图** `NSTitlebarContainerView` —— 日志显示"移了 3pt"
   但读数纹丝不动：AppKit 随后把那个容器摆回自己的位置。**改成只移按钮本身**。
2. 量中线也**必须量按钮**，不能量容器（两者中线可以不一致）。
3. 移完之后 AppKit 还会在若干时机重排标题栏，把按钮摆回去 —— 实测同一轮启动里
   能同时读到 19.0 和 16.0 两种状态。补 `windowDidBecomeKey` / `windowDidResize`
   都不够。**最终解法：`NSWindow` 子类重写 `layoutIfNeeded()`，排完立刻再对齐一次
   （自愈）**；已对齐（Δ ≤ 0.5pt）直接返回，不会递归。

验证方式：`DebugLayout` 开关把几何写进日志（本机 `screencapture` 被 TCC 挡住，
截不了屏，只能靠数字）。对齐后 `close centerFromTop` 与 `tabBar centerFromTop` 都是 19.0。

### 15.5 关窗口 → 段错误：`NSWindow.isReleasedWhenClosed` 默认为 true

**现象**：关掉设置窗（或关掉最后一个窗口）时整个 App 崩溃，系统弹「意外退出」。
崩溃报告里**一行我们自己的代码都没有**，主线程栈是：

```
objc_release → AutoreleasePoolPage::releaseUntil → objc_autoreleasePoolPop
             → -[NSAutoreleasePool drain] → -[NSApplication run] → SpacedownMain.main()
```

典型"多释放一次"，地址是垃圾指针。2026-10-08 起累计 5 份同样签名的报告
（也就是说**这个 bug 从最初版本就在**，不是后来某个改动引入的）。

**根因**：程序化创建的 `NSWindow`，`isReleasedWhenClosed` **默认为 `true`**（实测确认）。
关窗时 AppKit 释放窗口一次；而 `AppDelegate` 通过 `settings` / `main` 还持有一份**强引用**，
ARC 之后再释放一次 → 多释放。`windowWillClose` 里把强引用置 nil 正好让两条释放路径撞上，
所以「关窗」是触发条件。

**复现与验证**（最小程序，结构与 App 一致：`AppDelegate` 持控制器 → 控制器持窗口 →
`window.delegate` = 控制器 → `windowWillClose` 里置 nil →
`applicationShouldTerminateAfterLastWindowClosed = true`）：

| `isReleasedWhenClosed` | 关窗结果 |
|---|---|
| `true`（默认，即当时的代码） | **退出码 139（SIGSEGV）** |
| `false` | **退出码 0**，干净退出 |

**解法**：两个窗口都显式关掉它 —— `SpacedownWindow.init` 里设（这样以后新建主窗口也跑不掉），
`SettingsWindow` 里设（它是那个崩溃的直接责任人）。这不是"顺手加保险"：ARC 下持有窗口强引用时
**必须**设，Apple 的 ARC 迁移文档就是这么要求的。

⚠️ 想从崩溃报告直接看出是这里是不可能的（栈上没有业务代码）。判断办法就是
「关窗必崩 + 栈落在 pool drain」这个组合。

### 15.6 扩展没有沙箱权限 → 系统**静默不加载**它（空格预览显示别家的）

**现象**（2026-10-14，查了一整天才定位）：按空格预览 .md，出来的是 **WPS 的「金山文档」加载卡片**
（又慢又卡）；我们的扩展在 `os_log` 里**一行日志都没有**；系统设置的扩展面板里也**看不到它**。
而同一个文件**双击打开（主 App）一切正常**。

**根因**：`QuickLookPreview.appex` **没有 `com.apple.security.app-sandbox`** ——
`codesign -d --entitlements -` 显示它只有一个 ad-hoc 的 `get-task-allow`。
**macOS 不会加载没有沙箱的 App 扩展**，而且失败方式极其安静：不报错、不提示、扩展面板里也不列它。
于是系统退回去用**别家**已注册的扩展（本机是 WPS 的 `WPSQuickLook`），
用户看到的"慢、卡、金山"全都是 WPS 在渲染 —— 我们的代码根本没跑。

**判断依据（并排比对一个能用的实现）**：开源的 showmd 的扩展权限是

```
app-sandbox · application-groups(group.one.yetanother.showmd)
· network.client · files.user-selected.read-only
· temporary-exception.files.absolute-path.read-only = [/]
```

我们原来是**空的**。这就是"它装完就能用、我们怎么弄都不行"的全部差别。

**解法**：
1. 新增 `QuickLookPreview/QuickLookPreview.entitlements`（`app-sandbox` + `files.user-selected.read-only`）
2. 在 `scripts/gen_project.py` 的 `EXT_SETTINGS` 里挂 `CODE_SIGN_ENTITLEMENTS`（**必须走脚本**，
   工程是生成的）
3. 代码里读文件前补 `url.startAccessingSecurityScopedResource()` —— Quick Look 给的是
   **security-scoped** URL，沙箱下不 start 会直接 `operation not permitted`
4. 验证（这条能自查，不用按空格）：
   ```bash
   codesign -d --entitlements - /Applications/Spacedown.app/Contents/PlugIns/QuickLookPreview.appex
   ```
   看到 `com.apple.security.app-sandbox = true` 才算对。

⚠️ **别再往"扩展没启用"那个方向查**：`系统设置 → 通用 → 登录项与扩展` 里根本没有
「快速查看」这一行（本机 macOS 27 实测），而且扩展没被加载时那一类目压根不会出现。
先看 entitlements，再看优先级。

### 15.7 沙箱里的扩展打不开链接 → `LinkOpener.xpc`

删除「点击链接」这件事的两个层面，**第一层是 bug，第二层才是功能**。

**第一层：不拦的话预览会被网页顶掉。** CSP 的 `default-src 'none'` **管不住顶层导航** ——
`decidePolicyForNavigationAction` 里必须 `cancel`，否则点一下链接，web view 就导航走了。

**第二层：拦下之后得真的打开。** 而沙箱里的扩展**不能**调 `NSWorkspace`。实测
（最小探针：同一段代码，只差一个 `app-sandbox`）：

| | `NSWorkspace.shared.open(url)` |
|---|---|
| 不沙箱 | 返回 `true`，浏览器打开 |
| **沙箱** | **进程被 SIGTRAP 杀掉（退出码 133）** |

注意它不是"返回 false"——是**直接死**。所以这不是"失败可忽略"，是"点了就崩扩展"。

**解法**：`LinkOpener/` 一个 xpc-service，**刻意不带 app-sandbox**，只放行
`http` / `https` / `mailto`；协议文件同时编译进扩展与服务两边；扩展侧用异步代理调用。
同架构的 showmd（LinkOpener）与 QLMarkdown（external-launcher）都是这个结构。

**工程生成器里的坑**（`scripts/gen_project.py`，值都是试出来的，别照抄别处经验）：

| `dstSubfolderSpec` / `dstPath` | 落点 | 结果 |
|---|---|---|
| `16` / `""`（Xcode 界面上叫 Embed XPC Services 的那个值） | `<appex>/XPCServices/`（**bundle 根**） | ✗ 签名失败 `unsealed contents present in the bundle root` |
| `0` / `$(CONTENTS_FOLDER_PATH)/XPCServices` | 解析失败 | ✗ `The file "LinkOpener.xpc" doesn't exist` |
| **`1` / `Contents/XPCServices`** | `<appex>/Contents/XPCServices/` | ✓ |

`16` 是 **iOS 语义**（那边 bundle 根就是产品本身）；macOS 包必须把一切放在 `Contents/` 下。

**自查（不用按空格）**：
```bash
codesign -d --entitlements - <app>/Contents/PlugIns/QuickLookPreview.appex/Contents/XPCServices/LinkOpener.xpc
# 应当**看不到** app-sandbox（它就是靠"不在沙箱里"才能打开链接）
```
