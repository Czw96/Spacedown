## 二、安全与正确性（P1）

### 1. 危险 scheme 过滤漏掉单引号 / 无引号裸 HTML

`MarkdownRenderer.neutralizingDangerousURLs`

改成**按属性值处理**的逐字节重写（不再做 `href="` 的字面替换）：

- 覆盖 `"` / `'` / 无引号三种形态，以及 `=` 两侧的空白与属性名大小写
- 属性名边界判断，`data-href=` 这类自定义属性不会被误伤
- 重建路径也走在字节上，省掉 `String(cString:)` + `.utf8` 的两次全量拷贝
- 快速路径（`containsDangerousScheme` 字节扫描）保留，正常文档零额外成本

实测（`Bench --print`，输入 10 种形态）：

| 输入 | 输出 |
|---|---|
| `<a href="javascript:alert(1)">` | `href="#blocked-alert(1)"` ✅ |
| `<a href='javascript:alert(2)'>` | `href='#blocked-alert(2)'` ✅（原来漏） |
| `<a href=javascript:alert(3)>` | `href=#blocked-alert(3)` ✅（原来漏） |
| `<a href="JaVaScRiPt:alert(4)">` | `href="#blocked-alert(4)"` ✅ |
| `<a href = "javascript:alert(5)">` | `href = "#blocked-alert(5)"` ✅（原来漏） |
| `<a HREF="javascript:alert(6)">` | `HREF="#blocked-alert(6)"` ✅ |
| `<a href="vbscript:msgbox(1)">` | `href="#blocked-msgbox(1)"` ✅ |
| `<img src="data:text/html;base64,…">` | `src="#blocked-;base64,…"` ✅ |
| `<div data-href="javascript:alert(9)">` | **原样不动** ✅（不该动的没动） |
| 代码块里的字面量 | **原样保留** ✅ |

### 2. FileWatcher 在「删除后原地重建」时失聪

`FileWatcher` 改成**双源状态机**：

- 文件存在 → 盯文件本身（接住"原地写"，这是目录源接不到的）
- 文件消失 → 换盯**父目录**，等它回来
- 回来 → 停目录源、重挂文件源 → 触发刷新

原来的实现只在"新文件存在且 inode 变了"时才重挂，`rm` 掉再写回同名文件这一路会留着
一根盯着**已删除 inode** 的 fd，此后一个事件都收不到。

### 3. 滚动位置采集竞态

`WebViewPool.captureScrollY` 在回执里加了身份校验：只有「实例仍属于本标签」或
「已回收但内容尚未被换掉」才写入。**不能**简单写成 `contentOwner[view] == tab` ——
被回收的实例 `contentOwner` 已清空，一刀切会把该存的滚动位置丢掉。

### 4. 右键「关闭标签」关错标签

新增 `closeTabFromMenu(_:)`，用菜单项的 `tag`（= 右键命中的索引）而不是 `currentIndex`。

### 5. 宽表格破版

`SharedTheme.wrappingTables`（渲染期）给每个 `<table>` 套 `<div class="table-wrap">`，
CSS 侧 `overflow-x: auto`。代码块里的 `&lt;table` 不会误伤；markdown 表格不嵌套，
所以「第一个 `</table>` 是配对的」成立。打印时 `overflow: visible`，避免滚动条被烤进 PDF。

### 6. 标签栏溢出压到右侧控件

`TabBarView` 引入 `TabStripView` 容器，**裁剪与命中测试一起收进 bounds**：

- 只设 `layer.masksToBounds` 不够 —— AppKit 的 `hitTest` 按 `frame` 判定，
  被裁掉的标签照样点得中（会"跳到看不见的标签"），所以 `hitTest` 也一起收
- 宽度下限 92 → 62（这是"能读"的下限，不是排版下限），超出由容器裁掉
- `+ 新建`钉在标签区右缘，不再被顶到控件底下
- 右键命中测试改到容器坐标系

### 7.1 工具栏只留缩放

按你的截图，`TabBarView` 右侧的「在 Finder 中显示」（folder）与「用默认编辑器打开」

- 与标签区之间那条 1pt 分隔线保留 —— 它本来就是用来分开「新建标签的 `+`」和「放大的 `+`」的
- ⚠️ **功能本身没删**：两个动作仍在「文件」菜单里（<kbd>⌘⇧R</kbd> / <kbd>⌥⌘E</kbd>）。
  纯粹是把它们请出工具栏，不是砍掉能力。如果你想连菜单项一起删，说一声。

### 7.2 「放大」的快捷键原来是坏的 —— 实测证据

`MainMenu` 里「放大」写的是 `keyEquivalent: "+"`。**这个写法按不出来**：物理键盘上
并没有独立的 `+` 键，用户按的是 <kbd>⌘=</kbd> 或 <kbd>⇧⌘=</kbd>，而菜单匹配拿的是事件的
`charactersIgnoringModifiers` —— ⇧⌘= 的这个值就是 `"="`，永远匹配不到 `"+"`。

验证办法：构造 `NSEvent` 喂给 `NSMenu.performKeyEquivalent(with:)`，在
`主菜单 → 显示 → 菜单项` 的真实嵌套结构里跑。结果：

| 物理按键 | `keyEquivalent: "+"` | `keyEquivalent: "="` |
|---|---|---|
| <kbd>⌘=</kbd> | ✗ | ✅ |
| <kbd>⇧⌘=</kbd>（大家心里的「⌘+」） | ✗ | ✅ |
| <kbd>⌘+</kbd>（只有合成事件才可能） | ✅ | ✗ |

修法：**可见项保持 `"+"`**（负责把「⌘+」这四个字符显示出来，符合惯例），
再加一条 `isHidden = true` 的 `"="` 别名条目真正接键。
`NSMenuItem.isHidden` 只影响显示、**不影响键等价匹配**（实测确认），所以这样两全。

实测（真实嵌套结构 `主菜单 → 显示 → 项`）：

```
⌘= → 命中 ✓        ⇧⌘= → 命中 ✓        ⌘- → 命中 ✓        ⌘0 → 命中 ✓
⌘p（对照，不该命中）→ 未命中 ✗
可见菜单项： 放大 + | 缩小 - | 实际大小 0     ← 别名没有露出来
```

`⌘-` 与 `⌘0` 本来就正常（物理键与字符一一对应），不需要别名。

顺带把三个按钮的 tooltip 补上了快捷键：`缩小（⌘-）` / `放大（⌘+）` /
`点击回到 100%（⌘0）`。

编译 ✅、启动冒烟 ✅（`firstPaint 194.3ms`，标签 `180×30 @ x=78` 未变，无新崩溃报告）。

## 八、追加：缩放三件套的中线对齐（同日 16:18）

反馈原文：「加减号和中间的数字不在一个水平线上」。**不是错觉**，实测差 3pt。

### 8.1 先把问题量出来

你的截图是 @2x（394×76px = 197×38pt），按墨迹中线量：

| 元素 | 垂直墨迹中线 | 相对 `+` |
|---|---|---|
| `−` | 20.25 pt | +0.50 |
| **`100%`** | **16.75 pt** | **−3.00** |
| `+` | 19.75 pt | 基准 |

### 8.2 根因

`NSTextField` 的文字是**贴着框顶**排的（实测：墨迹顶 = 框顶 + `ascender` − `capHeight`），
而按钮里的 SF Symbol 是在 22pt 方框里**垂直居中**。旧代码把中间那格写成
`y: 9, height: 18`，跟按钮的 `y: 8, height: 22` 不是一套坐标，于是数字整体偏高。

### 8.3 试了三种写法（离屏渲染同尺寸工具栏后按像素量）

| 写法 | 数字相对 `+` 的墨迹中线偏差 |
|---|---|
| 旧：写死 `y: 9`、高 18 | 高 **2.75 pt** ← 就是看到的那条错位 |
| 直觉修法：把 label 的框对齐按钮的框 | 高 **3.75 pt** ← **更糟**，这个直觉是错的 |
| **本方案：按字体度量反推** | **0.5 pt 以内**（纯栅格化残差） |

定标验证：把同一个式子放大到 40pt 渲染，"cap 中线"设定 100.00，
实测墨迹 85.50–114.50 → **中线正好 100.00**。所以这个式子是精确的，不是凑出来的数。

### 8.4 落地的写法

```swift
// 框顶 = 「cap 高中线」− (ascender − capHeight/2)
let capMidToTop = zoomFont.ascender - zoomFont.capHeight / 2
frame = NSRect(x: x, y: centerY - capMidToTop, width: zoomLabelWidth, height: zoomBoxSide)
```

对齐的是**数字的 cap 高中线**（数字没有下伸部，墨迹就是 cap 高那一块），
所以 `60%` / `500%` 这类位数变化不影响结果。字体集中到 `TabBarView.zoomFont` 一个常量，
排版要用它的度量 —— 注释里写明了改字号必须改那里。

### 8.5 校验（两条独立证据）

1. **离屏渲染 + 加权质心**（按墨量加权，再补 0.5px 像素中心）：
   `−` 19.75 · `+` 19.01 · 数字 **旧 15.49 → 新 19.53**。
   数字落在两个符号的中点（距中点 0.15pt ≈ 0.3 物理像素）。
2. **真机 App**：`DebugLayout` 日志新增三行自检，实测三者**都是 19.0**：

```
zoom− centerFromTop=19.0
zoomLabel(cap 中线) centerFromTop=19.0
zoom+ centerFromTop=19.0
```

> 顺带说明：本机 `screencapture` 被 TCC 挡住（`could not create image from display`），
> 所以"差几个 pt"这类问题只能靠离屏渲染 + 日志数字来验收。上面第 2 条就是为此加的。

### 8.6 还留着的 0.74pt

`−`（19.75）与 `+`（19.01）两者自身的墨迹中线就差 **0.74pt** —— 这是 SF Symbols
两个字形在 11pt 下的光学/栅格差异，数字已经落在它们中间。要再抠就得去动
按钮的贴图位置，收益是 0.3 物理像素，不值得。
