# 性能：钱花在哪、哪些能动、"换技术栈"值不值

> 数字来源：`docs/benchmarks.md`（M0 / M1 两轮实测）。本文只做归因和决策，不重复记录原始数据。

---

## 0. 一句话结论

**我们自己写的代码只占 ~1ms，慢的全在 WebKit。**

| | 50KB README | 占整个"打开文件"的比例 |
|---|---:|---:|
| 读文件 + 解析 + 拼 HTML（我们的全部工作量） | **≈ 2 ms** | < 1% |
| WKWebView 那一侧 | **300 ~ 380 ms** | > 99% |

所以：
1. 优化预算 **100% 投在"进程与 webview 的复用"**，不是解析、不是缓存；
2. **不需要换技术栈** —— 渲染内核已经是纯原生 Swift + vendored C，非原生的只有 WebKit 这一层。
3. **但这条结论只管「首帧」。** 滚动是**另一笔账**：首帧是一次性成本（进程 + 排版），
   滚动是**每帧重绘**的持续成本 —— 预热与池化对后者一点用都没有。
   见 §6（2026-10-08 补测）。

## 1. 耗时账单（按量级排序）

| # | 环节 | 实测 | 性质 | 能不能省 |
|---|---|---:|---|---|
| 1 | **WebContent 进程 spawn** | **≈ 300 ms** | 一次性（进程起来后就一直在） | ✅ 预热 |
| 2 | **新建 `WKWebView` 实例** | **≈ 64 ~ 74 ms** | 每个新实例 | ✅ 池化复用 |
| 3 | **排版（大文件）** | 236 ms / MB(HTML) | 每篇、随体积线性 | ✅ 截断 |
| 4 | 同一 webview 二次导航 | ≈ 10 ms | 每次切换 | 已是池内路径 |
| 5 | cmark 解析 | 1.7 ms @50KB / 200 ms @5MB | 每篇、随体积线性 | 只有 5MB 才值得管，而 5MB 已被截断 |
| 6 | 读文件（mmap）+ 拼 HTML | < 1 ms | 每篇 | 忽略 |

> 第 1 名和第 5 名差 **4 个数量级**。这就是"押缓存是押错了"的全部原因：
> 缓存能省的是第 5 名（1.7ms），而第 1 名（300ms）跟缓存毫无关系。

## 2. 逐项：怎么省、省多少、代价

### 2.1 进程 spawn（300 ms）— 已解决

**做法**：App 一启动就建一个 webview 并导航到空白页，把 WebContent 进程先拉起来。

**为什么有效**：这 300ms 本来要在用户打开第一个文件时付。挪到启动阶段，与启动动画重叠，等于白拿。

**落点**：`Spacedown/Content/WebViewPool.swift` 的 `prewarm()`。

⚠️ **更正**（详见 `技术方案.md §15.3`）：**每个 `WKWebView` 独占一个 WebContent 进程**，
并不存在"多个 webview 共享一个渲染进程"这回事。所以预热不是"预热 1 个就等于预热全部"，
它省的是**进程启动的公共成本** —— dyld 绑定、系统框架与 WebKit 的首次映射/初始化；
这些成本在一个进程起来之后就进了系统缓存，与后续开几个进程无关。

实测印证这一点：

| 场景 | 首帧 |
|---|---:|
| 第一个文件（预热过的 webview） | **98.0 ms** |
| 第二个文件（**全新 webview、全新进程**） | **99.0 ms** |
| 完全冷启动（无预热） | 373.6 ms |

**新进程本身已经不贵了，贵的是第一份进程。** 这是池化与预热能同时成立的原因：
池化省下的是第 2 名的 74ms 实例创建与重排版（二次导航只要 10ms），
预热省下的是第 1 名那个"第一份进程"的价。

### 2.2 实例创建（74 ms）— 已解决

**做法**：LRU 池，容量 5，**淘汰不销毁**。

**为什么"不销毁"**：实测二次导航只要 10.2ms，而新建实例要 73.8ms，**差 7 倍**。
销毁一个实例省的内存（~30MB）远比它重建的时间便宜。所以淘汰时把实例摘下来放**备用区**，
下次要就直接给它 `load()` 新内容。

**代价**：常驻实例上界 = 5 + 2 = 7 个 ≈ 210 MB，压在 §1.1 里 P9 的 250 MB 目标内。

**落点**：`Spacedown/Content/WebViewPool.swift`。

### 2.3 大文件排版（236 ms/MB HTML）— 已缓解

**关键认知**：真正的天花板是**排版**，不是解析。HTML 约为 Markdown 的 1.85 倍，
所以排版 ≈ 437 ms × (Markdown MB)。1MB 的 Markdown 要 437ms，5MB 要 2.2 秒。

**唯一有效的缓解是截断**。原方案里"1~4MB 跳过图片内联与高亮"是错的 —— 成本是整篇排版，
跳过这些不解决任何问题。当前阈值 **512 KB**。

**落点**：`MarkdownDocument.bytes(contentsOf:maxBytes:)`。

### 2.4 落盘缓存 — 决定不做

原方案把缓存当"性能核心"，M0 实测推翻了：**能省的只有解析那一段**。

| Markdown | 缓存能省 | 说明 |
|---|---:|---|
| 50 KB | 1.8 ms | 相对 300ms 的进程 spawn 是零头 |
| 500 KB | 19 ms | 相对 237ms 的排版仍是零头 |
| 5 MB | 200 ms | **但 5MB 已经被截断了，走不到这条路** |

**结论：收益 ≈ 0，成本是一整套 stat 校验 / LRU 淘汰 / 跨进程共享目录**。不进 v1。
（§4 那一章保留作为设计记录，实现状态改为"不做"。）

### 2.5 静态链接去掉 2 个 dylib — 可做，优先级低

当前 App 要 `dlopen` 两个自有 framework（`MarkdownKit` / `SharedTheme`），
每次冷启动有 dyld 绑定 + 符号解析成本，量级 **5 ~ 15 ms**（一次性）。

改成静态库能拿掉这层，但要连带处理资源定位（`theme.css` 目前躺在 framework bundle 里，
改成静态库后要塞进宿主 bundle，而 appex 是独立 bundle 还得各带一份）。
**收益一次性、量级小，改动面不小** —— 排在截图/多标签/QL 验证之后。

### 2.6 Quick Look 扩展的进程复用 — 不由我们控制

QL 预览跑在系统管理的独立进程里，**它是否复用进程决定了数据型方案（方案 A）的首帧下限**。
唯一的观测手段是埋点日志里的 `pid`：

```
~/Library/Logs/Spacedown/timing.log
/tmp/spacedown-timing.log
```

同一个 `.md` 连按两次空格，看两行的 `pid`：
- **相同** → 进程被复用，二次预览 ≈ 解析耗时（几毫秒），数据型方案成立；
- **不同** → 每次都要付进程启动，那就要考虑方案 B（视图型 + 预热 webview）。

📌 **这一项还没拿到数据**（日志文件不存在），是目前最大的未知数。

## 3. 「换技术栈 / 用纯原生 Swift」的正面回答

### 3.1 现状：这条链路里没有 JS、没有 Electron

| 层 | 实现 | 语言 | 是否"原生" |
|---|---|---|---|
| Markdown 解析 | cmark-gfm 0.29.0.gfm.7（vendor 进仓库，`-O3 -mcpu=apple-m1`） | C | ✅ 原生 |
| 解析封装 | `MarkdownKit`（~40 行 Swift 包 C 指针） | Swift | ✅ 原生 |
| 主题 / HTML 外壳 | `SharedTheme`（CSS 字符串 + `Data` 拼接） | Swift + CSS | ✅ 原生 |
| 窗口 / 标签栏 / 池 | `Spacedown` target | Swift + AppKit | ✅ 原生 |
| **排版与渲染** | **WKWebView / WebContent 进程** | **系统框架** | ❌ **唯一的非原生层** |

所以"换成纯原生 Swift"这个说法，实际含义只能是一件事：**把 WKWebView 换掉**。

### 3.2 换掉 WKWebView = 走 NSTextView / TextKit 2

| | WKWebView | NSTextView + NSAttributedString |
|---|---|---|
| 冷启 | 40 ~ 250 ms | **20 ~ 40 ms** |
| 内存 | 50 ~ 100 MB | ~10 MB |
| GFM 表格 | ✅ 原生 | ❌ `NSTextTable` 做表格非常吃力 |
| 代码块 / 语言着色 | ✅ | 要自己写 |
| 裸 HTML（README 徽章、`<details>`、`<kbd>`） | ✅ | ❌ **整片丢失** |
| CSS 主题 | ✅ 一份 CSS 通吃明暗 | 要在 Swift 里重建一套样式系统 |

**这笔交易不成立**，两个理由：

1. **省下的正好是已经省掉的钱。** 换掉 WKWebView 能拿回的只有冷启那 300 + 74 ms ——
   而这两笔已经用「预热 + LRU 池」拿掉了。换完不会更快，只会更丑。
2. **保真度会塌。** 用户的定调是"markdown 渲染出来也要好看"。
   TextKit 路线下 GFM 表格、代码块、裸 HTML 都得自己重建，且**永远追不上 CSS**。
   方案 §8.2 已经因为这一条把它排除过一次。

> 顺带一提：只支持 M 系列之后，原来留着的那条"NSTextView 降级路径"已经**整个删掉了** ——
> 它当初存在的唯一理由是"Intel 老机可能不达标"，而这个目标机不存在了。

### 3.3 那"慢"的体感从哪来

按优先级排，用户的"慢"只可能是这三件事之一：

1. **QL 预览每次都要重新起扩展进程**（如果 pid 不复用）→ 见 §2.6，需要数据才能判断；
2. **主 App 里每打开一个文件都新建 webview**（改造前就是这样：一个文件一个 `DocumentWindow` + 一个 `WKWebView`，**没有任何复用**）→ **本次已修**；
3. **对照的 showmd**（已查其 GitHub 仓库）：`apple/swift-markdown` 解析 → HTML，并额外 bundle 了
   **highlight.js（190+ 语言）/ KaTeX / Mermaid** 三个 JS 库在渲染时执行；host app 是 SwiftUI
   设置窗，另有常驻菜单栏模式。要加载这些本地 JS/CSS，**几乎必然是视图型**（数据型返回的那段
   HTML 拿不到扩展 bundle 里的资源路径）—— 但这一点是从目录结构推断的，仓库里没有直接标注。
   如果 QL 复用进程，我们这种纯 HTML 数据型应该更快；如果不复用，我们反而更慢。
   **这就是 §2.6 那个埋点要回答的问题。**

### 3.4 同类软件都用什么渲染（2026-10 调研）

结论先行：**这个品类里没有一个用原生文本栈，全是 Web 渲染。**

| 软件 | 解析 | 渲染 | 备注 |
|---|---|---|---|
| **showmd**（对比对象） | `apple/swift-markdown` | HTML → QL 渲染（WebKit） | 额外 bundle highlight.js / KaTeX / Mermaid，**比我们更重** |
| **QLMarkdown**（relikd） | swift-markdown（cmark-gfm） | HTML → QL 渲染 | 6 MB；README 原话 "Output of the convert is passed, as is, to the preview window" |
| **QLMarkdown**（sbarex） | cmark-gfm 0.29.0.gfm.11 | macOS 12+ **数据型**；老系统**视图型**自建 `WKWebView` | 双路径 |
| **Marked 2 / MacDown** | 各自 | macOS **WKWebView** | |
| **Typora** | 自研（Pandoc 兼容） | **Electron**（Chromium + Node） | 冷启约 1.2 s、内存 150~300 MB |
| **Obsidian** | 自研 | **Electron** | |
| **VS Code 预览 / GitHub** | 各自 | **Chromium** | |

**为什么没人用 TextKit**：有一条流传很广的开发者记录（近 20 年 macOS/iOS 经验）把这条路完整走了一遍 ——
SwiftUI 做不了复杂文本选择 → 换 `NSTextView` + TextKit 2 → 流式文本有性能问题、出现闪烁的 cell
（且这是设计使然）→ 再下沉到 TextKit 2 底层 → 同样的问题 → **最后回到 WebKit，
"Markdown 渲染、排版、性能全都开箱即用"**。TextKit 2 社区里做过 Markdown 渲染 PoC 的人结论也一致：
**实现成本高、工作量大，多数人最终仍选择嵌入 web view。**

**三点启示**：

1. **WebKit 不是"慢的选择"，恰恰是 macOS 上冷启最便宜的 Web 渲染器** ——
   系统组件、磁盘只有一份、走 dyld 共享缓存、内存页可与 Safari/Mail 共享；
   而 Electron 要自带一整套 Chromium（150 MB+），冷启 1~2 s。
   我们 373 ms 的冷启已经比 Electron 快 3 倍以上。
2. **真正的敌人是"进程不复用"，不是"渲染器"** —— 这一点已用「预热 + LRU 池」解决（首帧 98 ms）。
   剩下唯一变量是 Quick Look 扩展的进程复用（§2.6，不由我们控制）。
3. **没有第三条路**：往回退是 TextKit（保真度塌、工程量大），往前走是 Electron（更慢更重）。
   **保持 WebKit + 把进程成本藏起来**，是这条链路上唯一正确的姿势。

## 6. 滚动（第二轮实测：2026-10-08）

**为什么会有这一节**：用户反馈「预览太慢、向下滚动画面太卡」。回看本文 —— 从 §1 到 §5
算的全是**首帧**。首帧和滚动是两笔不同的账：首帧是**一次性**成本（进程 + 整篇排版），
滚动是**每帧重绘**的持续成本。§2.1 的预热、§2.2 的池化，对滚动**毫无作用**。

### 6.1 测量工具：`ScrollBench`

`Packages/Core/Sources/DevTools/ScrollBench/`（已加进 `Package.swift`）：

```bash
cd Packages/Core && swift build -c release --disable-sandbox
.build/release/ScrollBench --file <preview.html> [--positions 40] [--only baseline,cv]
```

它把 HTML 载进真的 `WKWebView`，沿整篇高度均匀取样若干滚动位置，每个位置测两件事：

| 指标 | 怎么测 | 含义 |
|---|---|---|
| `layout95` | 改 `scrollTop` 后强制读一次布局属性 | **滚一步的同步重排**耗时 |
| `p50/p95` | `takeSnapshot(afterScreenUpdates: true)` 减 `false` | 强制重绘一屏；相减把图像编码这个常数抵掉 |

同时内置 10 个 CSS 变体（现状 / `content-visibility` / 表格 `border-collapse` /
去 `text-rendering` / 去 `:has()` / 去字体平滑 / 组合），**同一份文档横向对比**。

⚠️ **两条工具层的坑，都实际花过时间，记下来免得再踩**：

1. **`requestAnimationFrame` 需要 App 真的在跑事件循环。** 第一版用 rAF 量连续滚动，
   帧数全是 0。加探测发现 WebKit 自报 `document.visibilityState === "hidden"` ——
   `.floating` + `orderFrontRegardless` 不够，`activate(ignoringOtherApps:)` 也不够
   （`app.isActive` 一直是 false）。**真正的原因是本工具没跑 `NSApplication.run()`**：
   不跑就没有 display link，rAF 永不派发。
   修法：把测量整体搬进 `applicationDidFinishLaunching`，并用 **runloop 定时器**
   （不是 `DispatchQueue` block）触发 —— 从主队列 block 里嵌套泵 runloop 会让
   里面的加载直接超时（实测），从定时器回调里嵌套才是能用的（模态循环就是这么干的）。
2. **`callAsyncJavaScript` 传的是函数体，不是表达式。** 少了 `return` 会安静地返回
   `undefined`，于是所有数字都是 0（比报错更难发现）。
3. **页面被判 hidden 时 rAF 会被节流成 1Hz 左右**，量出来是「max 4627ms / 16s」这种
   假数字。看帧率时先确认 `visibilityState === "visible"`，否则整组数据作废。

### 6.2 实测数字（Apple Silicon）

**首帧**用既有的 `WebViewBench`（口径可信度高；`nav2` = 同一个已热 webview 再载一次，
即纯解析 + 排版；`wv2` = 新建 webview + 载入）：

| HTML | DOM 节点 | 文档高 | nav2（只解析+排版） | wv2（新建 webview+载入） |
|---|---:|---:|---:|---:|
| 64 KB（`docs/技术方案.md`） | 1,458 | 27,087 px | 23.5 ms | 115.1 ms |
| 306 KB | 10,183 | 171,562 px | 71.7 ms | 133.8 ms |
| 828 KB（512KB md 截断线的上限） | 27,991 | 471,563 px | 183.0 ms | 233.4 ms |

`cold` 那一列没列 —— 它被 WebContent 进程 spawn 主导，方差极大（实测 123~308 ms，与文件大小不成序）。

**滚动**用 `ScrollBench`（`--positions 24~40`，同一变体两轮之间能差 ±10 ms，**只看量级和相对差**）：

| HTML | 滚一步的同步重排 | 重绘一屏 p95 |
|---|---:|---:|
| 64 KB | 1.0 ms | 13.7 ms |
| 306 KB | 1.0 ms | 10.4 ms |
| 828 KB | 1.0 ms | 27.6 ms（max 33.9，5/24 个取样点超 16.7 ms 预算） |

**连续滚动帧率**（`--raf 3000`，脚本每帧滚 `--step` 像素，窗口确认 `visible`）：

| HTML | 节点 / 文档高 | 每帧 36 px（≈2160 px/s） | 每帧 150 px（≈9000 px/s，猛甩） |
|---|---:|---|---|
| 66 KB | 1.5k / 27k px | 180 帧，p50 17.0ms，**0 漏帧** | — |
| 306 KB | 10k / 172k px | 180 帧，p50 17.0ms，**0 漏帧** | 180 帧，**0 漏帧** |
| 828 KB | 28k / **472k px** | — | 180 帧，p50 17.0ms，**0 漏帧** |

> ⚠️ 注意第一组「重绘一屏 p95」和第三组「连续滚动 0 漏帧」并不矛盾：前者用
> `takeSnapshot` 把 IPC 往返 + 图像编码也算进去了，是个**含固定开销的上界**；
> 后者才是滚动路径的真实成本。**以帧率为准。**

### 6.3 能定下来的结论

1. **"慢"在排版，不在解析、也不在滚动路径。** warm webview 二次导航 23.5 → 71.7 → 183.0 ms，
   随 HTML 体积线性（≈ 0.22 ms/KB，与 §1 的 236 ms/MB 对得上）。
   在**数据型预览**里,这笔钱**每次按空格都要重付**（没有 webview 可复用，另加 64~74 ms 实例创建）。
2. **滚动不是排版慢**：每步同步重排恒定 **1.0 ms**，与文档规模无关。
   所以"优化解析 / 加缓存 / 换解析器"这条线对滚动零作用。
3. **CSS 层没有免费午餐**：去掉 `text-rendering: optimizeLegibility`、
   表格 `border-collapse` 改 `separate`、去掉 `:has()`、去掉 `-webkit-font-smoothing`
   —— 全部落在噪声内。**别再靠调 CSS 解决滚动。**
4. **`content-visibility: auto` 是负收益，别做**：
   - 文档高度虚高 **5 倍**（471,563 → 2,437,741 px），滚动条会跳；
     只作用在 `pre/table/blockquote` 上也仍虚高 1.36 倍（→ 642,270 px）；
   - 它把成本从"平均"挪成"**滚动那一刻的尖峰**"（该变体 `layout95` → 14 ms），
     恰好落在最不能卡的位置。
5. **`100~400 KB` 这一档正好是最坏区间**：转成 HTML 是 185~740 KB、
   1 万~2.5 万节点、17 万~45 万 px 高。而现状截断阈值是 **512 KB**，等于"几乎不截"。
6. **内容不是瓶颈 —— 这条是决定性的。** 在**viewport 尺寸**的 `WKWebView` 里，
   连 472k px 高的文档、以 9000 px/s 猛甩，也是 **60.0 fps / 0 漏帧**；
   每帧只重画一屏，成本与文档总长**无关**。
   ⇒ 用户感受到的「滚动卡」**不可能来自内容、CSS 或文档大小**，只能来自
   「**谁在承载这份 HTML**」。而数据型预览恰恰把 web view 的尺寸与滚动交给了系统 ——
   那是我们唯一控制不到、也从没验证过的环节。

### 6.4 埋点是零可见度（已修）

数据型那版用 `try?` 往 `~/Library/Logs/Spacedown/` 和 `/tmp/spacedown-timing.log` 写文件。
查过三件事：

- `strings` 确认**装到 `/Applications` 的 appex 带埋点代码**（能捞到
  `/Library/Logs/Spacedown/timing.log`，且与新建产物**逐字节一致**）；
- 用户在 Finder 里按空格，**出来的是我们的样式**（渲染页、克式中性色、单一靛紫强调色）——
  所以 `providePreview` 确实被调用了；
- 而两个日志路径**都是空的**（`~/Library/Logs/Spacedown/` 连目录都没建）。

⇒ **`TimingLog` 跑到了、两次写入都失败，被 `try?` 静默吞掉。** Quick Look 主进程会把
扩展进程关进沙箱，这两个路径都不在可写范围里。旁证：同类项目 sbarex/QLMarkdown 的

（`~/Library/Group Containers/...`）—— 那需要真签名 + Team，ad-hoc 拿不到。

⇒ **已改成 `os_log`**（统一日志在沙箱内可用）：

```bash
log stream --predicate 'subsystem == "cn.29dev.Spacedown"' --style compact
```

顺带作废一条旧验收：§2.6 那个"连按两次空格看 `pid` 是否复用"用文件埋点**永远拿不到数据**。

### 6.5 结论与已落地的改动

**根因**：不是内容、不是 CSS、不是文档大小（§6.3 第 6 条：同一份 HTML 在 viewport 尺寸的
`WKWebView` 里 60 fps / 0 漏帧）。问题是**数据型预览把 web view 的尺寸与滚动交给了系统**
—— 那是我们唯一控制不到、也从没验证过的一环。所以**把预览改成视图型，自己持有 web view**：

| 改动 | 位置 |
|---|---|
| 数据型 → **视图型**（`QLPreviewProvider` → `QLPreviewingController`） | `QuickLookPreview/PreviewViewController.swift`（原 `PreviewProvider.swift` 已删） |
| web view **永远是面板尺寸**，绝不按整篇高度撑开 | `loadView()`：frame = 容器 bounds + `.width/.height` 自适应 |
| **实例复用**（容量 1，退场后延迟 0.5s 回收；确认回收可达后才预热下一份） | `PreviewWebViewPool` |
| 埋点改 `os_log`，并输出 `read / render / wrap / load / total` 分段 | 同上 |
| Info.plist 去掉 `QLIsDataBasedPreview`，principal class 换成视图控制器 | `QuickLookPreview/Info.plist` |

**同时被实测否决、不要再走的路**：

| 路线 | 为什么否掉 |
|---|---|
| **CSS 微调**（去 `optimizeLegibility` / 表格改 `separate` / 去 `:has()` / 去自定义滚动条） | 全在噪声里。那张 60 fps 的表就是**用现有 CSS（含 `::-webkit-scrollbar`）跑出来的** |
| **`content-visibility: auto`**（一种"滚动加载"） | 文档高度虚高 5 倍（滚动条会跳）+ 把成本挪成滚动瞬间 14 ms 尖峰 |
| **HTML → PDF 交给系统** | 实测 485 ms / 1.1 MB（66KB 文档）、749 ms / 1.56 MB（306KB 文档）。生成成本随**总绘制面积**走，对"按空格扫一眼"太贵；还要付主题被烤死 + 分页（PDF 单页上限 200 英寸，47 万 px ≈ 4912 英寸） |
| **`contentSize` 调参** | 官方文档写明它只是给加载占位 UI 的**尺寸提示**，不是滚动开关 |
| **换渲染器**（TextKit / Electron） | §3 已否过一次；滚动成本来自承载方式，与渲染器无关 |

**还没做的**（等这一版真机验收后再决定）：

1. **截断阈值仍是 512 KB**，等于"几乎不截"。如果验收后"慢"还在，再把上限调到 ~200 KB
   （首帧 183 → ~70 ms），这是唯一还没有实测支撑、但收益明确的一步。
2. **分页渲染**（只把当前页附近的 DOM 交给 WebKit）：能让「9000 行」和「200 行」手感一致，
   但改变交互（滚动条变翻页），且必须先有视图型这层脚手架 —— 现在具备了，但没做。
