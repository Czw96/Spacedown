# 性能：钱花在哪、哪些能动、"换技术栈"值不值

> 数字来源：`docs/benchmarks.md`（M0 / M1 两轮实测）。本文只做归因和决策，不重复记录原始数据。

---

## 0. 一句话结论

**我们自己写的代码只占 ~1ms，慢的全在 WebKit。**

| | 50KB README | 占整个"打开文件"的比例 |
|---|---:|---:|
| 读文件 + 解析 + 拼 HTML（我们的全部工作量） | **≈ 2 ms** | < 1% |
| WKWebView 那一侧 | **300 ~ 380 ms** | > 99% |

所以：
1. 优化预算 **100% 投在"进程与 webview 的复用"**，不是解析、不是缓存；
2. **不需要换技术栈** —— 渲染内核已经是纯原生 Swift + vendored C，非原生的只有 WebKit 这一层。

---

## 1. 耗时账单（按量级排序）

| # | 环节 | 实测 | 性质 | 能不能省 |
|---|---|---:|---|---|
| 1 | **WebContent 进程 spawn** | **≈ 300 ms** | 一次性（进程起来后就一直在） | ✅ 预热 |
| 2 | **新建 `WKWebView` 实例** | **≈ 64 ~ 74 ms** | 每个新实例 | ✅ 池化复用 |
| 3 | **排版（大文件）** | 236 ms / MB(HTML) | 每篇、随体积线性 | ✅ 截断 |
| 4 | 同一 webview 二次导航 | ≈ 10 ms | 每次切换 | 已是池内路径 |
| 5 | cmark 解析 | 1.7 ms @50KB / 200 ms @5MB | 每篇、随体积线性 | 只有 5MB 才值得管，而 5MB 已被截断 |
| 6 | 读文件（mmap）+ 拼 HTML | < 1 ms | 每篇 | 忽略 |

> 第 1 名和第 5 名差 **4 个数量级**。这就是"押缓存是押错了"的全部原因：
> 缓存能省的是第 5 名（1.7ms），而第 1 名（300ms）跟缓存毫无关系。

## 2. 逐项：怎么省、省多少、代价

### 2.1 进程 spawn（300 ms）— 已解决

**做法**：App 一启动就建一个 webview 并导航到空白页，把 WebContent 进程先拉起来。

**为什么有效**：这 300ms 本来要在用户打开第一个文件时付。挪到启动阶段，与启动动画重叠，等于白拿。

**落点**：`Spacedown/WebViewPool.swift` 的 `prewarm()`。

⚠️ **更正**（详见 `技术方案.md §15.3`）：**每个 `WKWebView` 独占一个 WebContent 进程**，
并不存在"多个 webview 共享一个渲染进程"这回事。所以预热不是"预热 1 个就等于预热全部"，
它省的是**进程启动的公共成本** —— dyld 绑定、系统框架与 WebKit 的首次映射/初始化；
这些成本在一个进程起来之后就进了系统缓存，与后续开几个进程无关。

实测印证这一点：

| 场景 | 首帧 |
|---|---:|
| 第一个文件（预热过的 webview） | **98.0 ms** |
| 第二个文件（**全新 webview、全新进程**） | **99.0 ms** |
| 完全冷启动（无预热） | 373.6 ms |

**新进程本身已经不贵了，贵的是第一份进程。** 这是池化与预热能同时成立的原因：
池化省下的是第 2 名的 74ms 实例创建与重排版（二次导航只要 10ms），
预热省下的是第 1 名那个"第一份进程"的价。

### 2.2 实例创建（74 ms）— 已解决

**做法**：LRU 池，容量 5，**淘汰不销毁**。

**为什么"不销毁"**：实测二次导航只要 10.2ms，而新建实例要 73.8ms，**差 7 倍**。
销毁一个实例省的内存（~30MB）远比它重建的时间便宜。所以淘汰时把实例摘下来放**备用区**，
下次要就直接给它 `load()` 新内容。

**代价**：常驻实例上界 = 5 + 2 = 7 个 ≈ 210 MB，压在 §1.1 里 P9 的 250 MB 目标内。

**落点**：`Spacedown/WebViewPool.swift`。

### 2.3 大文件排版（236 ms/MB HTML）— 已缓解

**关键认知**：真正的天花板是**排版**，不是解析。HTML 约为 Markdown 的 1.85 倍，
所以排版 ≈ 437 ms × (Markdown MB)。1MB 的 Markdown 要 437ms，5MB 要 2.2 秒。

**唯一有效的缓解是截断**。原方案里"1~4MB 跳过图片内联与高亮"是错的 —— 成本是整篇排版，
跳过这些不解决任何问题。当前阈值 **512 KB**。

**落点**：`MarkdownRenderer.documentBytes(contentsOf:maxBytes:)`。

### 2.4 落盘缓存 — 决定不做

原方案把缓存当"性能核心"，M0 实测推翻了：**能省的只有解析那一段**。

| Markdown | 缓存能省 | 说明 |
|---|---:|---|
| 50 KB | 1.8 ms | 相对 300ms 的进程 spawn 是零头 |
| 500 KB | 19 ms | 相对 237ms 的排版仍是零头 |
| 5 MB | 200 ms | **但 5MB 已经被截断了，走不到这条路** |

**结论：收益 ≈ 0，成本是一整套 stat 校验 / LRU 淘汰 / 跨进程共享目录**。不进 v1。
（§4 那一章保留作为设计记录，实现状态改为"不做"。）

### 2.5 静态链接去掉 2 个 dylib — 可做，优先级低

当前 App 要 `dlopen` 两个自有 framework（`MarkdownKit` / `SharedTheme`），
每次冷启动有 dyld 绑定 + 符号解析成本，量级 **5 ~ 15 ms**（一次性）。

改成静态库能拿掉这层，但要连带处理资源定位（`theme.css` 目前躺在 framework bundle 里，
改成静态库后要塞进宿主 bundle，而 appex 是独立 bundle 还得各带一份）。
**收益一次性、量级小，改动面不小** —— 排在截图/多标签/QL 验证之后。

### 2.6 Quick Look 扩展的进程复用 — 不由我们控制

QL 预览跑在系统管理的独立进程里，**它是否复用进程决定了数据型方案（方案 A）的首帧下限**。
唯一的观测手段是埋点日志里的 `pid`：

```
~/Library/Logs/Spacedown/timing.log
/tmp/spacedown-timing.log
```

同一个 `.md` 连按两次空格，看两行的 `pid`：
- **相同** → 进程被复用，二次预览 ≈ 解析耗时（几毫秒），数据型方案成立；
- **不同** → 每次都要付进程启动，那就要考虑方案 B（视图型 + 预热 webview）。

📌 **这一项还没拿到数据**（日志文件不存在），是目前最大的未知数。

## 3. 「换技术栈 / 用纯原生 Swift」的正面回答

### 3.1 现状：这条链路里没有 JS、没有 Electron

| 层 | 实现 | 语言 | 是否"原生" |
|---|---|---|---|
| Markdown 解析 | cmark-gfm 0.29.0.gfm.7（vendor 进仓库，`-O3 -mcpu=apple-m1`） | C | ✅ 原生 |
| 解析封装 | `MarkdownKit`（~40 行 Swift 包 C 指针） | Swift | ✅ 原生 |
| 主题 / HTML 外壳 | `SharedTheme`（CSS 字符串 + `Data` 拼接） | Swift + CSS | ✅ 原生 |
| 窗口 / 标签栏 / 池 | `Spacedown` target | Swift + AppKit | ✅ 原生 |
| **排版与渲染** | **WKWebView / WebContent 进程** | **系统框架** | ❌ **唯一的非原生层** |

所以"换成纯原生 Swift"这个说法，实际含义只能是一件事：**把 WKWebView 换掉**。

### 3.2 换掉 WKWebView = 走 NSTextView / TextKit 2

| | WKWebView | NSTextView + NSAttributedString |
|---|---|---|
| 冷启 | 40 ~ 250 ms | **20 ~ 40 ms** |
| 内存 | 50 ~ 100 MB | ~10 MB |
| GFM 表格 | ✅ 原生 | ❌ `NSTextTable` 做表格非常吃力 |
| 代码块 / 语言着色 | ✅ | 要自己写 |
| 裸 HTML（README 徽章、`<details>`、`<kbd>`） | ✅ | ❌ **整片丢失** |
| CSS 主题 | ✅ 一份 CSS 通吃明暗 | 要在 Swift 里重建一套样式系统 |

**这笔交易不成立**，两个理由：

1. **省下的正好是已经省掉的钱。** 换掉 WKWebView 能拿回的只有冷启那 300 + 74 ms ——
   而这两笔已经用「预热 + LRU 池」拿掉了。换完不会更快，只会更丑。
2. **保真度会塌。** 用户的定调是"markdown 渲染出来也要好看"。
   TextKit 路线下 GFM 表格、代码块、裸 HTML 都得自己重建，且**永远追不上 CSS**。
   方案 §8.2 已经因为这一条把它排除过一次。

> 顺带一提：只支持 M 系列之后，原来留着的那条"NSTextView 降级路径"已经**整个删掉了** ——
> 它当初存在的唯一理由是"Intel 老机可能不达标"，而这个目标机不存在了。

### 3.3 那"慢"的体感从哪来

按优先级排，用户的"慢"只可能是这三件事之一：

1. **QL 预览每次都要重新起扩展进程**（如果 pid 不复用）→ 见 §2.6，需要数据才能判断；
2. **主 App 里每打开一个文件都新建 webview**（改造前就是这样：一个文件一个 `DocumentWindow` + 一个 `WKWebView`，**没有任何复用**）→ **本次已修**；
3. **对照的 showmd 用的是视图型扩展**（常驻 webview），而我们是数据型 —— 如果 QL 复用进程，
   数据型应该更快；如果不复用，我们反而更慢。**这就是 §2.6 那个埋点要回答的问题。**
