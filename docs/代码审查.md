## 结论摘要

代码整体质量高于同规模个人项目：性能决策都有实测依据、注释把"为什么"写清楚了、
已知坑（`@main` / baseURL 死锁 / 进程数）都有留档。**没有发现会导致崩溃或数据损坏的高危问题**，

以及**内容侧表格溢出、标签栏溢出两块"肉眼可见"的 UI 缺陷**。

## 一、结构与可读性

### A1 ⚠️ 截断逻辑重复，且违背了它自己的约定（P2）

`MarkdownRenderer.documentBytes` 的注释明确写着：

> 放在这里而不是各自调用方：Quick Look 扩展和主 App 的截断口径**必须一致**，否则同一个文件两处显示会不一样长。
> —— `MarkdownRenderer.swift:11-12`

但 `PreviewViewController` 完全没走它：

| 位置 | 内容 |
|---|---|
| `PreviewViewController.swift:68` | `private static let maxBytes = 512 * 1024`（第二份常量） |
| `PreviewViewController.swift:395-411` | 自己 `Data(contentsOf:)` + 自己判断超限 |
| `PreviewViewController.swift:414-422` | `truncated(_:limit:)` —— 与 `documentBytes` 逐行同构的第三份实现 |
| `PreviewViewController.swift:419` | 提示文案 `"文件过大，已截断显示前 … KB"` 也抄了一份 |

现在两处都是 512KB，所以看不出差异；一旦哪天放宽到 1MB 而漏改一处，
同一个文件在主 App 和空格预览里就会**显示成不同长度** —— 这正是注释里想避免的事。

**改法**：`render(url:)` 里换成 `try MarkdownRenderer.documentBytes(contentsOf: url)`，删掉 `maxBytes`/`truncated`/提示文案。

### A2 死代码（P2）

### A3 诊断代码留在主线（P2）

## 二、潜在漏洞与错误

### B1 ⚠️ 危险 scheme 过滤漏掉单引号 / 无引号裸 HTML（P1，安全）

`neutralizingDangerousURLs`（`MarkdownRenderer.swift:160-179`）只做**字面替换**：

```swift
for attr in ["href=\"", "src=\""] {          // ← 只认双引号
    out = out.replacingOccurrences(of: attr + scheme, with: attr + blockedFragment, …)
}
```

问题在于：我们开了 `CMARK_OPT_UNSAFE`（`:63`），**裸 HTML 是原样输出的**。于是

```html
<a href='javascript:alert(1)'>点我</a>
<a href=javascript:alert(1)>点我</a>
```

这两串既不会被替换掉，`containsDangerousScheme`（`:193-210`）**却会命中**并进入重建分支 ——
重建又改不动它们，等于白白走一遍昂贵路径后照样放过。

**当前不会立刻被打穿**，因为还有第三层：CSP `default-src 'none'`（`Theme.swift:48`）在 WebKit 下
会挡 `javascript:` 导航。但这意味着**三层防护的第二层事实上是漏的** —— 只要哪天
把 CSP 放宽（例如为了远程图片改 `img-src *`），这个缺口就会变成真漏洞。

**改法**：属性匹配不再依赖引号形状（正则/字节扫描找 `href=` 后到空白或 `>` 的子串做前缀判断），
或在渲染后对裸 HTML 统一过一遍属性级清洗；并把单引号、无引号、大小写 `JaVaScRiPt:` 写成回归样例。

### B2 ⚠️ FileWatcher 在"删除后原地重建"场景会失聪（P1，功能）

`settle()`（`FileWatcher.swift:93-109`）：

```swift
if now.exists && now.inode != entry.stamp.inode {
    stop(url); start(url)          // ← 只有"新文件存在"才重挂
} else {
    entries[url]?.stamp = now
}
guard now.exists else { return }   // ← 文件不存在时，旧 fd 仍留在 entries 里
```

覆盖不到的场景：编辑器/脚本先 `rm` 再写同名文件（或 rename 走了再回来）。
此时走 `else` 分支，`entries[url]` 里的 `DispatchSource` **仍然盯着已被删除的旧 inode**，
再也收不到事件 → **该标签之后永远不会自动刷新**，用户只能手动 ⌘R。

**改法**：`!now.exists` 时同样 `stop(url)` 并移除 entry（下次 `watch()` 重挂），
或把"inode 变化"与"从无到有"合并成统一的重挂条件。

### B3 ⚠️ `captureScrollY` 与回收/复用存在竞态（P1，状态污染）

`WebViewPool.captureScrollY`（`:132-139`）是**异步**的：

```swift
Task { @MainActor in
    if let raw = try? await view.evaluateJavaScript("window.scrollY") { tab.scrollY = … }
}
```

而调用方紧接着就回收：`MainWindow.select`(:218) / `closeTab`(:236) / `evictOverflow`(:153) →
`retire`/`pushSpare` 会清掉 `contentOwner`，实例回到备用区，**随时可能被下一个标签 `acquire` 并 `load()` 新内容**。
那次 `window.scrollY` 读到的就可能是**另一个标签**的滚动位置，被写回旧标签的模型 →
切回去时滚动到莫名其妙的位置。备用区溢出时实例还会被 `loadHTMLString("")` 清空，读到 0。
两个方向都是错的。

**改法**：`load()` 之前 await 一次采集、或给采集加代次校验（`entries` 记录 token，回调时比对）。

### B4 ⚠️ 右键菜单"关闭标签"关的是当前标签，不是右键那个（P1，功能）

`tabMenu(for:)`（`MainWindow.swift:266-282`）：

```swift
menu.addItem(withTitle: "关闭标签", action: #selector(closeCurrentTab(_:)), keyEquivalent: "")
```

而 `closeCurrentTab`(:443) 用的是 `currentIndex`。**在非当前标签上右键 → 点"关闭标签" → 关掉的是另一个标签**。
（同菜单里的"关闭其他标签"是正确带 `tag` 的，只有这一条漏了。）

**改法**：加一个 `@objc closeTabFromMenu(_ sender: NSMenuItem)`，`tag` 传 index。

### B5 ⚠️ 宽表格没有横向滚动容器（P1，内容 UI）

`theme.css:281` 只给了 `table { width: 100% }`，而 `pre` 有 `overflow-x: auto`（:183）——
两者不对称。结果是：**宽表格（本项目的 benchmark 表就是典型）在 Quick Look 窄面板里会撑破版心**，
要么把整页撑出横向滚动、要么被裁掉右侧列。这是"按空格扫一眼"场景下最容易看到的破版。

**改法**：在 `SharedTheme.document`（或渲染期）把每个 `<table>` 包一层
`<div class="table-wrap" style="overflow-x:auto">`。纯字符串包装、不引入 JS、成本可忽略。
详见 §四 D1。

### B6 ⚠️ 标签栏数量多时会与右侧控件重叠（P1，UI）

`TabBarView.layout()`（`TabBar.swift:237-266`）宽度被夹在 `[92, 180]`：

```swift
let width = min(maxTabWidth, max(minTabWidth, (available - spacingTotal) / CGFloat(items.count)))
var x = tabsStart
for item in items { item.frame = …; x += width + tabSpacing }
newTabButton.frame = NSRect(x: x + 4, …)
```

当 `n` 大到 `(available - spacing)/n < 92` 时，宽度被**钳到 92 不再收缩**，而 `x` 继续增长 ——
标签会一路画到右侧缩放/动作按钮**上面**（item 是后添加的，图层更高），`+ 新建`按钮也被顶到控件之下。
没有裁剪、没有滚动、没有溢出提示。详见 §四 D2。

### B7 `.md` 打开面板的可选类型过窄（P2）

`openDocument`（`MainWindow.swift:436-438`）把 `allowedContentTypes` 设成
`[UTType("net.daringfireball.markdown")]`。但本机实测（`技术方案.md:346-354`）：

| 扩展名 | 实际 UTI |
|---|---|
| `.mdown` `.mkd` | `com.kingsoft.wpsoffice.markdown`（WPS） |
| `.mkdn` `.rmd` `.qmd` `.mdx` | `one.yetanother.showmd.*` |

这些都不是 `net.daringfireball.markdown` → **在打开面板里会被灰掉/选不中**，且没有
`allowsOtherFileTypes = true` 兜底。而 QL 扩展侧同理（`Info.plist:37` 只列了一个 UTI）。

**改法**：面板允许 `public.text` 并做后缀白名单校验（比放 `public.plain-text` 安全），
或直接 `allowsOtherFileTypes = true`；扩展侧按文档自己的结论补 `public.markdown`。

### B8 空状态文案承诺了不存在的功能（P2）

`MainWindow.swift:111`：`"把 .md 拖进来，或按 ⌘O 打开"`。但全工程
`registerForDraggedTypes` / `NSDraggingDestination` / `performDragOperation` **零命中** ——
**拖放根本没实现**。用户按提示拖进来会毫无反应。

**改法**：实现拖放（`webHost` 或 window 注册 `.fileURL`，校验后缀后 `open(url)`，约 20 行），
或先把文案改成 `"按 ⌘O 打开 Markdown 文件"`。推荐做前者 —— 拖放是这类工具的高频入口。

### B9 `SharedTheme` 打包缺失即 `fatalError` 崩溃（P2）

`Theme.swift:30,35` 两处 `fatalError`。这对主 App 尚可（启动即崩、能立刻发现），
但对 **Quick Look 扩展**偏激进：扩展崩溃的代价是 Finder 预览链路抖动。
建议 CSS 缺失时退回一份内联最简样式并写 `os_log`，让面板至少能出内容。

### B10 淡入淡出可能残留 alpha≈0 的 webview（P3）

`present()`（`MainWindow.swift:286-329`）：快速连续切换时，上一代的收尾任务被
`fadeGeneration` 挡掉（`:324`），被淡到 0 的实例不会立刻 `removeFromSuperview`，
要等下一次 `present` 的 `for extra in others where extra !== outgoing` 顺手清掉。
一般能自愈，但短时间内视图树里会叠着 alpha=0 的 `WKWebView`；
AppKit 对 alpha=0 视图的命中测试行为不完全可靠，理论上有吞滚轮/点击的风险。
建议收尾改成"遍历兄弟节点，非目标一律移除"，不依赖单一代次。

### B11 边界情况备忘（均不构成 bug，但值得知道）

- `truncated` 若前 512KB 内**没有任何换行**，`lastIndex(of: 0x0A)` 为 nil → 整段保留；
  且加上提示语后总长会**略超** `maxBytes`（`MarkdownRenderer.swift:25-31`）。
- `FileWatcher.start` 里 `open(O_EVTONLY)` 失败（文件已被删/无权限）时静默 return，
  该文件此后不再被监听，且无任何日志。
- `failureHTML`（`MainWindow.swift:538-543`）只转义 `&` 与 `<`。文本上下文足够；
  若将来把它放进属性里需补转义。
- `/tmp/spacedown-ql-diag.jsonl` 在共享目录里记录**文件名**，属轻微隐私面（见 A3）。

## 四、UI：布局 / 样式 / 交互 / 视觉一致性

### D1 表格：缺横向滚动容器（P1，**内容侧最该修的一条**）

见 B5。补一个 `.table-wrap { overflow-x: auto; margin: 0 0 1.5em; }` 并把
`table { margin: 0 }`，效果是宽表在窄面板里**可横向滚动而不是破版**。
连带可以顺手处理：`th { white-space: nowrap }`（:299）在窄容器里会加剧溢出，
配合 wrap 之后可以放宽为 `normal`。

### D2 标签栏：溢出与溢出后的降级（P1）

见 B6。建议按优先级做三件事：

1. `minTabWidth` 在放不下时允许继续收缩（例如下限放到 44px，只留首字母 + tooltip 全名）
2. 仍放不下则**在 `tabsEnd` 处裁剪**（`wantsLayer` + `masksToBounds`，避免盖住右侧控件）
3. 更完整的做法是横向滚动或"溢出菜单"（列出其余标签），成本更高，可放 v1.1

### D3 当前标签的关闭按钮应常驻（P3）

`TabItemView.setHovered`（`TabBar.swift:122-127`）把关闭按钮完全绑在 hover 上，
**当前标签也是 hover 才出现**。macOS/Chrome 的惯例是当前标签的关闭按钮常驻、
非当前标签 hover 才出现。改成 `closeButton.isHidden = !(hovered || isCurrent)` 即可，一行。

### D4 标签按下即切换，丢掉了两个交互（P3）

`TabItemView.mouseDown`（`:94-98`）注释写明"不在这里 performDrag"，
但代价是：① 与 AppKit "按下并抬起都在同一标签内才触发"的习惯不符（误触更贵）；
② 标签**永远无法拖动重排**；③ 没有中键关闭标签（浏览器肌肉记忆）。
建议改在 `mouseUp` 判定是否仍在自身 bounds 内，并可选支持中键。

### D5 图标与 UI 强调色不同源（P2，品牌一致性）

| 元素 | 取值 | 出处 |
|---|---|---|
| App 图标出厂色 | **`black` 炭灰**渐变 `#4E4E52 → #2C2C30` + 白标记 | `design/logo/build_logo.py:108,114` |
| UI 强调色 | **靛紫** `#4f46c9` / `#9b93f2` | `Palette.swift:15`、`theme.css:40,56` |
| 标签栏顶部 2px 条 | 靛紫 | `TabBar.swift:117` |

图标是中性灰、UI 是紫 —— 两者没有共同的色彩线索。`COLORWAYS` 里**已经有**
`indigo ("#6E6CE0","#3C3BBA")`（`:101`），所以两条路都是一行改动：

- **路线 A（更克制）**：把 UI 强调色改为与图标同族的中性/石墨，让"唯一强调色"更收敛
- **路线 B（更统一）**：把 `PRIMARY` 改成 `'indigo'` 并重跑 `build_logo.py`，让图标与 UI 同源

建议选 B：图标已经定稿过一次（`0c08940`），换色号只需改 `PRIMARY` 一行 + 重跑脚本，
而"图标与界面同色"对品牌一致性的收益远大于换一次色号的风险。

### D6 自定义滚动条可能反而更"非 macOS"（P2，一致性）

`theme.css:361-378` 给 `::-webkit-scrollbar` 定义了固定 11px 宽、带 3px 描边的滑块。
方案文档里"实测在噪声里"针对的是**帧率**，但**样式上**：一旦覆盖 `::-webkit-scrollbar`，
WebKit 就用**经典常驻滚动条**，不再是 macOS 的 overlay 自动隐藏样式 ——
在 Finder 里"按空格扫一眼"的场景下，一根常驻的粗滚动条和系统观感是割裂的。

建议做一次对照（`ScrollBench` 已经能出图，或直接在 Finder 预览里看）：
① 保留现状 ② 完全移除自定义滚动条（用 overlay） ③ 收到 8px。三者选一并与方案文档同步。

### D7 空状态太弱（P3）

`MainWindow.swift:111-114` 只有一行 tertiary 灰字。既然 `AppIcon.icns` 已接入，
空状态可以做成：**64~80px 图标 + 一行主文案 + 一行 kbd 快捷键**（`<kbd>⌘O</kbd>` 在内容 CSS 里
已有样式，但空状态是 AppKit 侧，需要用 `NSAttributedString` 或一张小图）。
这是"第一印象"最划算的一处改动。

### D8 首次打开缺少加载反馈（P3）

首帧要 60~300ms（`技术方案.md:14`），期间内容区是纯底色。虽然 `underPageBackgroundColor`
已经把白闪压掉了，但"什么都不动"和"正在加载"用户分不清。建议在 `webHost` 上叠一个
很轻的 `NSProgressIndicator(.spinning)`，`didFinish` 后隐藏；或让 webview 首帧淡入 0.15s。
⌘R 重载同理。

### D9 无障碍与焦点（P3）

- `TabItemView` 没有 accessibility role/label（`NSTextField` 文本会落到 label，但不含"标签页"语义）
- `zoomLabel` 可点击重置（`TabBar.swift:299-300` 的 `NSClickGestureRecognizer`），
  但**没有任何 tooltip 提示**"点一下回到 100%"，纯靠猜
- `+`（新建标签，pointSize 11）与 `+`（放大，pointSize 11）**同形不同义**
  （`TabBar.swift:180,182`），只靠 tooltip 区分，视觉上容易误认

建议：新建标签换 `plus.square` 或加一条视觉分隔；缩放三件套后加一条 8px 高的竖分隔
（和"在 Finder 中显示 / 用编辑器打开"再隔开）；`zoomLabel.toolTip = "点击回到 100%"`。

### D10 快捷键 `⌘+` 需要确认（P3）

`MainMenu.swift:53` 用 `"+"` 作 keyEquivalent。macOS 上物理按键是 `⇧⌘=`，
AppKit 对 `"+"` 与 `"="` 的处理在菜单显示与触发上略有差异。建议实测三种输入
（`⌘+`、`⌘=`、`⇧⌘=`）哪一种能触发；若只认一种，可再加一条 `"="` 的隐藏别名项。

### D11 尺寸与字号的口径（P3）

| 项 | 现状 | 备注 |
|---|---|---|
| 设置窗字号 | 12.5（`SettingsWindow.swift:90,107`） | 标签栏用 12、缩放用 11 —— 12.5 是第三档 |
| 设置窗 Logo | 92px（`:79-82`） | macOS 惯例是 64 / 128 |
| `--measure` | 44rem 且 `box-sizing: border-box`（`theme.css:91`） | 含 3rem×2 内边距 → 实际行宽 ≈ 608px（≈34 个中文字） |
| `.content` 底边距 | `padding … 6rem`（`:93`） | 比顶边 2.5rem 大不少，读到文末会有明显的"空落感"，属刻意为之即可 |

### D12 缩放的实现语义（P3）

`setMagnification`（`MainWindow.swift:415-423`）走 `webView.magnification`（GPU 合成层缩放），
符合方案 §6.3。但 `clamped` 上下限是 `0.25 / 5.0`，而**菜单/标签栏没有任何提示**当前已到边界
（按到底毫无反应）。建议到边界时把 `zoomLabel` 或 `+`/`−` 按钮短暂变灰（`isEnabled = false`）。
